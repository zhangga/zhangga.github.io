Chapter 01 · Mental Model

症状不是结论调试不是猜 CVar，而是建立一条证据链

“敌人在 Client 1 偶发消失”只是用户看到的现象。它既可能没有进入这条连接的 relevant 集合，也可能属性没有变脏、条件屏蔽了成员、预算没写进去、包丢了，甚至数据已经到达，只是客户端应用或 RepNotify 出了问题。

SYMPTOM客户端看到敌人消失，生命值偶尔过期。
OBSERVE固定实例、连接、对象与复现时间，保留日志和 trace。
LOCATE证明阻断发生在 identity、relevant、dirty、write、packet 还是 apply。
EXPLAIN用源码契约解释为什么这一层拒绝、跳过、积压或浪费。
PROVE只改变一个变量，用相同场景做修改前后对照。
“服务器上对象存在”不等于“它对 Client 1 relevant”；“包里写过属性”也不等于“客户端已经应用”。每跨一层，都要补一份证据。

最危险的排障方式是看到对象消失就提高 Cull Distance，看到更新慢就抬 Priority，看到丢包就增加带宽。这些调整可能暂时遮住症状，却让真实错误和容量成本一起进入生产环境。正确顺序是：先找到断点，再改控制断点的机制。

CORRECTNESS

功能正确性

对象、属性或 RPC 是否沿完整链路到达正确连接，并在正确上下文中应用。

PERFORMANCE

单位工作成本

过滤、轮询、量化、优先级和写入各花多少时间，是否与有效产出匹配。

CAPACITY

规模与增长

对象数、连接数、KBytes、队列与内存增加时，成本是否线性且可回落。

Chapter 02 · Observability Stack

先问问题，再选仪器日志、快照、时间线与聚合各自看见什么

同一个工具不可能回答所有问题。对象打印命令提供某一时刻的快照；日志提供有顺序的离散事件；Insights 还原时间线和 packet 内容；CSV 擅长长时间聚合与版本对比；LLM 负责内存归属。把工具用错尺度，通常只会得到更多噪声。

问题首选工具得到的证据不能直接证明
对象是否注册、句柄是什么PrintNetInfoOfObject对象、类、NetRefHandle、协议与依赖过去某一帧是否发出
为何只对某连接消失对象命令 + ConnectionIdrelevant、filter、cull、priority数据包是否到达客户端
哪一阶段 CPU 高Timing Insights线程、scope、持续时间与调用关系哪个属性占了最多 bits
包里到底写了什么Networking Insightsconnection、packet、object、property、RPC压缩后真实 wire bytes
哪个类型长期昂贵Iris CSV / NetStats按类型的 time、count、KBytes、waste单个对象某一帧的完整因果链
内存增长记到哪里LLM / Memory InsightsIris 标签、时间曲线、allocation query仅凭标签上涨认定泄漏

三种观察尺度

SNAPSHOT

现在是什么

对象命令和调试器状态适合回答“这一刻的相关性、内部状态和依赖是什么”。

TIMELINE

什么时候发生

日志与 Insights 用于还原事件先后、帧尖峰、packet 到达和线程执行。

AGGREGATE

长期花在哪里

CSV 与 LLM 适合比较场景、版本、对象类型、连接规模和稳态斜率。

推荐的缩放顺序

先用对象名找到 NetRefHandle，再锁定 RepSystemId 与 ConnectionId，最后才扩大到 trace 和聚合。不要先打印整场所有对象的 VeryVerbose 日志，再从海量文本里碰运气。

Chapter 03 · End-to-End

每一层只证明一件事一次属性更新的七个检查点

下面这条流水线是本篇的总地图。某一检查点成立，只允许继续调查下一站；不允许越过它直接宣布“网络层没问题”。

01 · IDENTITY注册与身份

对象已注册到正确 ReplicationSystem，具有有效 NetRefHandle 与 Protocol。

02 · SCOPE连接相关性

目标 Connection 有效，对象通过 owner、group、dynamic filter 与 cull。

03 · CHANGE变化被发现

dirty、poll 与成员 condition 共同产生本连接可见的 ChangeMask。

04 · SCHEDULE调度与预算

prioritizer 给出 priority，对象在 packet budget 内获得发送机会。

05 · WRITE量化与写入

状态 quantize，引用和 creation info 准备完成，内容进入 outgoing packet。

06 · RECEIVE接收与解析

客户端收到 packet，引用可解析，reader 接受对象状态。

07 · APPLY应用与通知

dequantize 到外部状态，属性写回，必要的 RepNotify 在正确时机执行。

检查点首选证据失败时优先调查
IdentityPrintNetInfoOfObject 找到对象与句柄注册时机、bridge、对象生命周期
Scope指定 Connection 的 relevant / filter 输出owner、group、dynamic filter、cull
Changequantized state、dirty/poll/condition 日志Push Model 标记、poll frequency、成员条件
Schedulepriority、writer info、scheduled/replicated 统计prioritizer、budget、队列、依赖
WriteNetworking Insights outgoing Packet ContentChangeMask、引用导出、writer / huge object
Receiveincoming packet、reader info、解析日志丢包、引用未解析、creation dependency
Apply客户端状态、RepNotify/RPC CSV 与断点dequantize、apply、RepNotify、Gameplay 覆盖
一个对象“relevant”只说明它有资格进入后续调度；它不承诺本帧必发，也不承诺属性条件允许，更不承诺客户端已收到。

Chapter 04 · 15.1

网络游戏的“隐形杀手”先把偶发问题变成可重复实验

功能缺陷往往只在某个连接、某个相对位置、某种对象生命周期和一次网络抖动下出现；性能问题则常被平均帧时间淹没。最小复现不是缩短测试步骤，而是固定会改变证据含义的变量。

常见问题清单

OBJECT

对象级

只对部分连接缺失、进入距离不出现、离开后不销毁、SubObject 生命周期错位。

MEMBER

成员级

属性值过期、Push Model 漏标 dirty、条件复制屏蔽、RepNotify 不触发。

BUDGET

容量级

候选对象远多于实际写入、Poll/Write Waste、可靠窗口或 huge object 队列阻塞。

一张合格的复现卡

Scenario = Enemy enters cover volume and loses line of sight Build = Development Editor / UE 5.7.4 Topology = Dedicated Server + 2 Clients RepSystemId = 0 ConnectionId = 1 Object = BP_Enemy_C_2147482471 NetRefHandle = 2010 Trigger = Client 1 crosses marker A at frame 18420 Window = 10 seconds before / 15 seconds after Emulation = Off Expected = enemy stays relevant; Health reaches 65 Observed = enemy hidden for 2.1 s; Health remains 80

PIE 中可能同时存在多个复制系统；不记录 RepSystemId，很容易在错误的 Server/Client 实例上打印。多连接会话不记录 ConnectionId，则“对任意连接 relevant”会掩盖目标玩家的独有问题。

Chapter 05 · 15.2

网络复制的“黑匣子”日志要围绕对象、连接和时间窗口采集

UE 日志既能在 Output Log 中查看，也会写入项目的 Saved/Logs。Iris 的基础公开类别包括 LogIris、LogIrisFiltering、LogIrisNetCull、LogIrisFilterConfig 与 LogNetStats。

源码内部还存在 LogIrisRepNotify、LogIrisConditionals、LogIrisGroup、LogIrisRpc、LogIrisReferences、LogIrisChunkedDataStream 和 LogIrisDirtyTracker。其中部分是静态类别，且输出受编译期 verbosity 影响；不要把每个内部名字都当作长期稳定的公开诊断接口。

七档有效 verbosity

Fatal终止
Error错误
Warning警告
Display控制台 + 日志
Log日志
Verbose详细
VeryVerbose极详细

All 常用于类别的编译期上限或配置，不是第八种普通消息严重度。

运行时与启动时配置

log LogIris VeryVerbose运行时调整基础 Iris 类别
log LogIrisFiltering Verbose缩到过滤决策
-LogCmds="LogIris VeryVerbose,LogIrisFiltering Verbose"从启动阶段开始采集
VeryVerbose 不是“信息更多所以更好”

它可能产生显著日志 I/O 和大量无关行。先在普通级别确认对象与连接，再只为短复现窗口提高目标类别；采集完成后恢复级别。Shipping 中可用输出还受编译裁剪与控制台策略限制。

敌人消失案例怎么读日志

  1. 以复现卡的服务器时间或帧为中心截取窗口；
  2. 搜索对象名与 NetRefHandle，确认是同一个实例而不是同类对象；
  3. 搜索目标 ConnectionId，区分全局状态与逐连接决策；
  4. 把 filter、condition、writer、reader 行按顺序排回七检查点；
  5. 保存完整原始日志，并单独记录做过的筛选条件。
日志最有价值的不是某一行“看起来像错误”，而是它能把同一个对象在同一连接上的决策按时间重新串起来。

Chapter 06 · 15.3

精准停在那个对象或 RPC 上IrisDebugHelper 把海量调用缩成条件断点

IrisDebugging.h/.cpp 提供了对象名、RPC 名、NetRefHandle 与内部索引四种筛选入口。主要实现位于 #if !UE_BUILD_SHIPPING，定位是开发构建调试，而不是 Shipping 线上诊断。

入口匹配对象行为关闭
Net.Iris.DebugName对象名或类名 substringBreakOnObjectName 触发断点，也可用于 filter设为空字符串
Net.Iris.DebugRPCNameRPC plain name substringBreakOnRPCName 触发断点设为空字符串
Net.Iris.DebugNetRefHandle 2010句柄 IDBreakOnNetRefHandle 触发断点命令不带参数
Net.Iris.DebugNetInternalIndex 42内部 object indexBreakOnInternalNetRefIndex命令不带参数
名称匹配是 contains，不是正则

DebugName=Enemy 会匹配名称中包含 Enemy 的对象或类。如果场景中实例很多，先用 PrintNetInfoOfObject 找句柄，再切到 DebugNetRefHandle，通常更精确。

调试器里可以直接调用什么

OBJECT

对象与句柄

DebugNetObject、DebugNetObjectById、DebugNetRefHandle、DebugNetRefHandleById。

STATE

内部量化状态

DebugOutputNetObjectState 与 DebugNetObjectStateToString 输出 Iris 内部 state。

PROTOCOL

协议与引用

DebugOutputNetObjectProtocolReferences 用于检查协议引用和使用者。

内部量化状态不是 Gameplay 对象内存的逐字节镜像。它使用 Replication Protocol、Instance Protocol 与序列化上下文解释 state，适合验证“引擎认为当前待复制值是什么”。字符串版本使用调试缓冲区，不应作为线程安全或长期持有的业务 API。

推荐断点流程 1. PrintNetInfoOfObject FindByName=... → 得到 NetRefHandle 2. Net.Iris.DebugNetRefHandle 2010 3. 在 BreakOnNetRefHandle / 目标 phase 附近附加调试器 4. 复现一次 5. 调用 DebugNetRefHandleById(2010, 0) 查看对象信息 6. 命令不带参数，关闭 handle 条件

Chapter 07 · Object Drill-Down

UE 5.7.4 的单对象入口先用 PrintNetInfoOfObject，再扩大到全局清单

ObjectReplicationBridgeDebugging.cpp 收集了多组对象诊断命令。旧式流程常先打印所有 replicated/relevant objects；在 UE 5.7.4 中，信息更密集的 Net.Iris.PrintNetInfoOfObject 更适合作为第一站。

Net.Iris.PrintNetInfoOfObject FindByName=BP_Enemy_C_2147482471 RepSystemId=0 ConnectionId=1按实例名 + 指定复制系统与连接
Net.Iris.PrintNetInfoOfObject FindByClass=BP_Enemy_C RepSystemId=0 ConnectionId=1,2按类 substring，包含继承关系
Net.Iris.PrintNetInfoOfObject FindById=2010 RepSystemId=0 ConnectionId=1已知 NetRefHandle 时精确查询

一条命令能给出哪些切面

IDENTITY

对象与 State

NetRefHandle、Protocol、量化状态，以及服务端或客户端 bridge 侧信息。

CONNECTION

逐连接资格

relevant 状态、filter、priority、ReplicationWriter / Reader 信息。

CONTEXT

空间与依赖

world location、cull distance、delta compression、parent/child 与 creation dependencies。

大纲命令的准确用法

命令适合回答常用参数
Net.Iris.PrintReplicatedObjects哪些对象已注册到 IrisRepSystemId、WithSubObjects、排序参数
Net.Iris.PrintRelevantObjects哪些对象对任意连接 relevantRepSystemId、WithSubObjects
Net.Iris.PrintRelevantObjectsToConnection目标连接看见哪些对象ConnectionId=1,5,7、WithFilter
Net.Iris.PrintAlwaysRelevantObjects全连接 always relevant 集合RepSystemId
Net.Iris.PrintNetCullDistances类与对象的当前 cull distanceNumClasses=20
Net.Iris.PrintPushBasedStatuses哪些类/属性没有采用 Push BasedRepSystemId
Net.Iris.PrintDynamicFilterClassConfig类会分配哪个 dynamic filterRepSystemId

多数命令支持 RepSystemId=X、WithSubObjects、SortByClass 与 SortByNetRefHandle。ConnectionId 可接受逗号分隔列表；未指定时，连接型信息通常扩展到有效连接集合。

PrintPushBasedStatuses 不能证明某次写入已经标脏

它能指出类或属性是否配置为 Push Based，却不能证明具体 mutation 调用了正确的 MARK_PROPERTY_DIRTY。具体属性不同步仍要沿 dirty → condition → ChangeMask → packet → apply 检查。

Chapter 08 · Trace

时间与内容是两副镜头Timing Insights 找 CPU，Networking Insights 找 bits

IrisProfiler 在默认配置下把宏映射到 CPU Profiler Trace scope，它不是独立 GUI。CPU 调查进入 Timing Insights；包、对象、属性和 RPC 的网络内容调查进入 Networking Insights。

CPU LENS

Timing Insights

观察线程、帧与 scope：过滤是否突然变慢，PollAndCopy 是否扩张，Quantize 或 UpdateDataStreams 是否形成尖峰。

BIT LENS

Networking Insights

选择 game instance、connection 与 incoming/outgoing，查看 packet 时间线、对象、属性、RPC 和 Net Stats Counters。

启动 NetTrace

-trace=net -NetTrace=1 -tracehost=localhostEditor/本机 Trace Server 的常用入口
NetTrace.SetTraceVerbosity 2运行时调到 Verbose
值枚举建议用途边界
0None关闭 NetTrace没有网络 trace 事件
1Trace常规 packet/content 调查首选起点
2Verbose需要更深层事件与计数器数据量上升
3VeryVerbose对象级 poll/quantize/write 深挖非 Shipping/Test 默认编译上限

UE 5.7.4 源码中，非 Shipping/Test 的 NetTrace 编译期上限默认是 VeryVerbose，Shipping/Test 默认是 Verbose；运行时设置会被编译期上限裁剪。

Networking Insights 的五个观察面

  1. Packet Overview：包的时间、大小、序号与 dropped 状态；
  2. Packet Content：对象、属性、RPC 与层级事件占用的 bits；
  3. Connection Selection：PIE/NetDriver 实例、连接与 incoming/outgoing；
  4. Net Stats：选区内事件的 total/max 与 inclusive/exclusive bits；
  5. Net Stats Counters：frame stats 与 packet stats，例如候选对象和实际装包对象。
Packet Overview 的大小是压缩前统计

Epic 5.7 文档明确说明，界面报告的 packet size 是压缩前内容，实际 wire data 可能更小。它非常适合做对象/属性相对归因，但不能直接替代平台抓包或压缩后带宽测量。

Chapter 09 · 15.4

时间 × 数量 × 数据量CSV 与 NetStatsContext 把尖峰变成可比较指标

Timing Insights 擅长逐帧和调用关系，CSV 更适合较长窗口、自动化场景和版本回归。Iris 的 CSV 统计不是只给一个总耗时，而是把 time、count 与 KBytes 分开；三者必须一起读。

TIMEMS

PreUpdate、Poll、Quantize、Write 花了多少 CPU 时间。

SCALECOUNT

处理了多少对象、写了多少状态、连接规模多大。

OUTPUTKBYTES

写入、creation info 与 waste 转化成多少数据。

CsvProfile Start开始采集
CsvProfile Stop结束并写入 Saved/Profiling/CSV
CsvProfile Frames=600固定帧数采集，适合对照

阶段时间数量数据量

客户端详细统计

客户端类别包括 IrisClient、IrisClientDetailObjectCreate、IrisClientDetailRepNotify、IrisClientDetailRPC 与 IrisClientBlockedByAsyncLoading。后者能记录对象等待异步资源加载的阻塞事件。

net.Iris.EnableDetailedClientProfiler 1按对象名、RepNotify 或 RPC 名细分；默认不面向 Shipping

FNetTypeStats 如何处理并行

并行 phase 中，每个工作单元从 FNetTypeStats 取得 child FNetStatsContext，完成后归还；帧末把 child 累加到 parent，再输出 CSV。这样能保留按类型归因，又避免所有任务竞争同一个非线程安全上下文。

SubObject 默认归入 Root 类型

net.Iris.Stats.ShouldIncludeSubObjectWithRoot 默认是 true。需要单独观察 SubObject 类型时可设为 0，但修改统计口径后，前后两次 CSV 不能直接混比。

分析比率，而不是新的引擎 Stat

单位 Poll 成本 = PollMS / PollCount 单位 Write 成本 = WriteMS / WriteCount 每连接成本 = TotalCost / ReplicatingConnectionCount 调度转化率 = ReplicatedRootObjectCount / ScheduledRootObjectCount 有效写入率 = 1 - (WriteWasteKBytes / TotalAttemptedWriteKBytes)

这些是调查时计算的派生比率，不是 UE 内置同名指标。它们的价值在于区分“对象变多导致总时间上涨”和“每个对象变贵了”。

Chapter 10 · Cost Attribution

昂贵不一定浪费，浪费也不一定是 Bug用产出解释 Poll、Write 与预算

如果只看到 PollMS 或 WriteMS 高，很容易误判。必须再问：处理量是否同步上涨？产生了多少有效状态？是否真正写进包？是否因为连接预算、mask 或对象作用域反复做无效工作？

信号常见含义下一份证据可能的行动
Poll Waste 高轮询了对象但没有有效变化按类型 PollWaste、poll frequency、PushBased status降低静态类型轮询，正确使用 Push Model
Write Waste 高尝试写入但状态被 mask、预算或 scope 排除write count/KBytes、writer info、packet counters减少无效候选，检查 condition 与预算
Scheduled ≫ Replicated候选规模远大于每帧实际可装包规模priority 分布、connection budget、积压时间改善过滤、优先级或状态频率
Creation/Export 突发大量对象首次出现或引用首次导出场景事件、Packet Content、对象创建数平滑生成、减少引用图或预热
Huge wait/stall大对象等待 ACK 或阻塞发送队列Active/Waiting/Stalling、可靠窗口、丢包拆分状态、降低可靠大负载、验证丢包恢复

FNetSendStats 与 FReplicationStats

UE 5.7.4 会报告每连接平均 scheduled / replicated root objects、replicated objects、destruction infos、masked-out states、delta compressed objects 和 active connections；同时跟踪 huge object 的 active、waiting、stall 数量与时间。复制系统还输出 pending objects、pending dependencies 与 huge object send queue 的平均值和峰值。

SCALE PROBLEM

Count 与时间同涨

总成本主要由规模驱动。优先减少候选、轮询频率或每连接 relevant 集合。

UNIT COST

时间涨，Count 不涨

单对象更贵。检查协议复杂度、动态数组、引用、任务并行与缓存行为。

LOW YIELD

时间涨，KBytes 不涨

有效产出低。重点看 Poll/Write Waste、condition、mask 和预算拒绝。

Waste 是调查入口，不是自动优化目标

某些对象必须定期 poll 才能保证正确性；某些候选会因逐连接预算而合理延后。只有在同一业务负载、相同连接数与相同统计口径下，Waste 的持续上涨才有可比较意义。

IrisMemoryTracker.cpp 用 LLM 标签标注 Iris 相关分配，并把它们汇总到 Networking summary。标签回答“这块内存记到哪一类”，不会自动回答“为什么没有释放”。

Iris ├─ State [unique: IrisState] ├─ Initialization [unique: IrisInitialization] ├─ Connection [unique: IrisConnection] └─ NetTokenStructState [unique: NetTokenStructState]
-LLM启用 Low-Level Memory Tracker
-LLMCSV启用并持续写入 Saved/Profiling/LLM
stat LLMFULL显示全部 LLM 统计
DumpLLM把当前与峰值标签大小写入日志

CSV 写入间隔可由 LLM.LLMWriteInterval 调整。Epic 5.7 文档说明 LLM 在 Shipping 中完全禁用；它应在 Development/Test 诊断流程中使用，而不是假设生产 Shipping 默认保留。

标签上涨怎么解释

标签先与什么归一化健康信号异常信号
IrisStateactive replicated objects / protocols对象销毁或场景卸载后回落对象数稳定但 State 持续爬升
IrisConnectionvalid / replicating connections断连后按连接回落反复连接后基线阶梯式上升
IrisInitialization初始化批次、descriptor/protocol 数加载完成后趋稳稳态 Gameplay 中持续增长

Iris先拆子标签父标签由可解释子项构成父标签上涨但子项与工作负载不匹配

从归属到泄漏证据

  1. 建立空场景、目标场景和卸载后稳态三段基线；
  2. 同时记录对象数、连接数和 token 规模；
  3. 确认增长来自哪个 Iris 子标签；
  4. 断连、销毁或卸载后观察是否回落；
  5. 在 Memory Insights 中对增长区间做 allocation query，并检查 callstack；
  6. 用相同循环次数验证修复前后的稳态基线。
“IrisConnection 上涨”只是一条归属证据。只有连接数已恢复、等待窗口结束，而同类 allocation 仍跨循环存活，才开始接近泄漏结论。

Chapter 12 · 15.6

让团队按同一顺序排查对象、属性与性能三套标准 Runbook

RUN 01

对象没有复制到目标客户端

  1. 确认服务器对象存在且生命周期未结束；
  2. 执行 PrintNetInfoOfObject FindByName=... RepSystemId=... ConnectionId=...；
  3. 找不到句柄：调查 bridge 注册、支持类型和创建/销毁时机；
  4. 句柄有效但不 relevant：调查 owner、group、dynamic filter、cull 与 dependency；
  5. relevant 但未写：查看 priority、writer、scheduled/replicated 与 packet budget；
  6. outgoing 有对象：在 Networking Insights 切到目标客户端 incoming；
  7. incoming 有数据但未创建：调查引用解析、creation dependency、factory/bridge receive。
RUN 02

对象存在，但属性没有同步

  1. 在服务端确认 Gameplay 值确实改变，而且不是随后被本地逻辑覆盖；
  2. 确认属性进入 Replication Descriptor，Push Based 属性是否正确标 dirty；
  3. 检查 poll frequency、dirty tracker 与 quantized internal state；
  4. 对目标 Connection 检查成员 condition、owner/autonomous/custom 条件；
  5. 在 outgoing Packet Content 查找对象与属性；
  6. 在 incoming 侧确认 packet 到达且 reader 接受；
  7. 在客户端检查 dequantize/apply、RepNotify 与 Gameplay 后续覆盖。
RUN 03

复制功能正确，但服务器出现性能尖峰

  1. 用 Timing Insights 定位慢 phase，而不是先猜对象类型；
  2. 用 CSV 的 time + count 判断是规模增加还是单位成本增加；
  3. 按类型查看 PreUpdate、Poll、Quantize、Write 与 Waste；
  4. 检查 scheduled/replicated 转化、连接数、pending 与 huge object 队列；
  5. 用 Networking Insights 验证高成本是否转化成有效 packet content；
  6. 必要时用 LLM 检查连接与状态容量是否同时异常；
  7. 固定场景、连接数和统计口径，做修改前后对照。

把正确性带进坏网络与发布流程网络仿真、检查清单与命令速查

一次只改变一个网络变量

先单独测 80ms lag，再单独测 5% loss，最后才组合。若一开始同时加 lag、loss、order、duplication，就无法知道哪个条件触发了失败，也无法证明修复针对了什么。

本篇结论

PROOF

逐层证明

身份、连接资格、变化、调度、写入、接收、应用，每层都有自己的证据。

MEASURE

三维度量

性能必须同时看时间、数量和数据量，再用对象类型与连接规模归因。

REPEAT

可重复实验

固定场景与采集窗口，一次改变一个变量，用相同证据验证修改前后。

成熟的网络调试不是“我试了一个命令，问题好像没了”，而是团队能回答：哪一层阻断、证据是什么、修改改变了什么、坏网络下是否仍成立。
