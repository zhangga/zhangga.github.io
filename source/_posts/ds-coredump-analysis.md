# DS 崩溃分析 · AI + 飞书自动化流程（脱敏版）

> 一套把 **Linux 专用服务器（DS）core dump 崩溃分析** 全流程自动化的方案：飞书报警卡片 → AI（`ds-coredump-analysis` skill）逐个分析 → 结论落库多维表格 → 回群通报。让"有 coredump 需要下载"的 P1 告警从人工排查变成流水线化处理。

- 适用引擎：Unreal Engine（`<项目名>` DS，Linux ELF core + gdb）
- 文档版本：2026-08-07
- 关键组件：飞书群机器人卡片、`ds-coredump-analysis` skill、落库工具、多维表格
- 说明：本文为**对外分享脱敏版**，机器路径、版本标识、飞书群 ID、多维表格链接、IP/集群等已用占位符（形如 `<xxx>`）替代，实际值以内部配置为准。

## 1. 背景与目标

线上 DS 崩溃会产生 core dump，运维监控在飞书群里以 **P1 告警卡片**推送（标题：`<告警标题>`，示例："服务有 coredump 文件需要下载"），卡片含 coredump 下载地址、日志地址、机器信息等。

痛点：人工逐个下载 core、配符号、跑 gdb、翻日志、写结论，重复且慢；相同根因反复排查。

目标：
- **自动拉取**告警卡片，按规则筛选出待分析项。
- **AI 自动分析**：结合 `core + gdb + 日志` 定位第一因，判断"何时崩、崩在哪"。
- **结论沉淀**：写入多维表格，跨次聚合共性崩溃，已分析过的直接复用。
- **闭环通报**：把结果链接发回飞书群。

## 2. 整体架构

```text
┌─────────────────────┐
│  飞书群 (P1 告警卡片) │  监控推送：coredumpurl / logfileurl / filename / ip / cluster ...
└──────────┬──────────┘
           │ ① 拉取最近 N 条卡片（按规则筛选）

│  │  0.5 卡片取数 (wget core/log, 版本→二进制) │  │
│  │  1  日志优先 (无 logfileurl 则跳过)        │  │
│  │  2~7 gdb 环境/栈/内存/FName/回源码          │  │

└──────────┬───────────────────────┬──────────┘
           │ ② 结论摘要 + 报告链接    │ 知识库/索引（本地随 skill）
           ▼                        ▼
┌─────────────────────┐   ┌────────────────────────┐
│  多维表格 (落库工具)    │   │ analyzed_cores_index.md │
│  每条 core 一行         │   │ crash_patterns.md       │
```

三层职责：
- **飞书层**：输入（卡片）+ 输出（表格、通报）。
- **AI 分析层**：`ds-coredump-analysis` skill，纯分析逻辑，自包含。
- **知识层**：filename 幂等索引 + 崩溃模式库，随 skill 目录携带，跨次累积。

## 4. 端到端流程

### 步骤 ① 拉取并筛选告警卡片

从飞书群 `<飞书群 ID>` 拉取标题为 `<告警标题>` 的卡片，按时间**从新到旧**：

- 累计**最多 10 个"未分析过"的 core**；
- 一旦遇到卡片时间早于 `当前时间 - 24h`（按 `Asia/Shanghai`）**立即停止**（即使不足 10 条）；
- 二者**先触发者为准**；
- **去重键 = 卡片中的 core `filename`**（全局唯一），先查 `analyzed_cores_index.md`，命中即跳过并继续往前拉。

### 步骤 ② 逐个分析（ds-coredump-analysis skill）

- 先**尽快下载**全部待分析 core（`coredumpurl` 带 `Expires` 签名，过期即 403），再逐个跑 gdb；
- 按 core 版本选**对应带符号二进制**，无法确定时用默认版本并在报告注明；
- **卡片无 `logfileurl` → 跳过日志分析、不找本地日志、直接 gdb**；
- **单条失败**（下载 403 / build-id 不匹配 / gdb 报错）→ 记录失败原因，**继续下一条**，不中断整批。

### 步骤 ③ 结论落库

用落库工具把每条结论**摘要 + HTML 报告链接**写入多维表格；完整 gdb/日志原文放报告正文，不塞进单元格。

### 步骤 ④ 回群通报

把表格链接发回群，说明本次：**扫描卡片时间范围（最早 → 最晚）、分析条数、跳过条数（已分析）、失败条数**。

## 6. skill 内部分析流程（步骤 0~12）

核心原则：**日志优先**——有日志时，不允许直接拿 core 原生栈下结论，先从日志定位最早第一因；无 `logfileurl` 时例外，直接 core + gdb。

| 步骤 | 内容 | 关键点 |
|---|---|---|
| 0 | 适用触发条件 | ELF core / gdb / SIGSEGV / `?? ()` / 飞书卡片 |
| **0.4** | **按 filename 查重** | 全局唯一幂等键；命中已分析过 → **直接返回历史结论**，跳过下载与 gdb |
| **0.5** | 从飞书卡片取数 | 解析字段 → `wget` 下载 core/log → 版本→二进制映射；**无 `logfileurl` 分支** |
| 1 | 先读日志找方向 | ①定版本 ②倒查第一因 ③识别业务路径 ④判定战场阶段 ⑤算存活时长；先回查知识库 |
| 2 | 环境准备 | `?? ()` 头号排查：二进制版本、build-id、依赖 `.so`、`.gdbinit`、符号就位 |
| 3 | 获取原生栈 | `bt` / `bt full` / `thread apply all bt` / `info registers` |
| 4 | 逐帧下钻 | GC 崩溃套路：DrainValidated → PushReference → ProcessObjects，找持有链根 |
| 5 | 内存取证 | `x/16gx` 对象头、`x/8gx` 失效引用、`find` 定位字段偏移 |
| 6 | 解码 FName → 类名 | `GNameBlocksDebug` 手动解，拿到 `BP_xxx_C` 类名 |
| 7 | 回项目源码定位 | Grep C++/TS/蓝图，排查 UPROPERTY/销毁清空/TS 回填；区分第一因 vs 级联 |
| 8 | 日志回扣验证 | 拿 core 结论回日志印证触发路径，闭环第一因（无日志则跳过） |
| 9 | 复现与加固建议 | `-gcdefaultverify` / `-stompmalloc` / ASan / `obj refs` |
| 10 | **输出 HTML 报告** | 见 §7 |
| 11 | 聚合归档到知识库 | 生成崩溃签名 → 登记 filename 索引 → 回查去重计数 → 回填修复状态 |
| 12 | 关键纪律（防幻觉） | 结论必须有 gdb 输出/源码证据支撑，无法验证标"未验证" |

### 无日志分支

部分卡片不含 `logfileurl`：**不做日志分析、不去本地机器翻找日志**，直接用 core + 对应版本带符号二进制走 gdb（跳过步骤 1、8，从步骤 2 开始），报告标注「无日志，仅 core 分析」，置信度不高于「高概率」。

## 7. 报告结构（HTML）

最终报告为**自包含单文件 HTML**（内联 CSS、浏览器直接打开），gdb/日志原文放 `<pre><code>` 代码块保留原格式，中文字体 `Noto Sans CJK SC` / `WenQuanYi Micro Hei`。

结构（从时间线 → 崩溃现场 → 原始证据层层递进）：

1. **崩溃发生时机（开头必答）**
   - 战场阶段：开局加载/进场 · 战斗进行中 · 结算/收尾 · 切换 `EmptyLoad` 退出卸载关卡 · 空闲待机 · 无法判定
   - 判定依据：core filename 关卡标识（`st_Empty`→切 EmptyLoad 退出；`st_<关卡名>`→对应战场）+ 日志结尾业务动作
   - **战场存活时长**：以日志最后一次 `receive agent ALLOCATED_NOTIFY` 时间戳为起点，算到日志末行的间隔（如"约 3 分 12 秒"）；无则「无法计算」
2. **基础信息**：CrashType / ErrorMessage / Version / Cluster·IP·Port / app_id / 崩溃时刻
3. **第一因 / 级联问题 / Native 栈状态**
4. **结论置信度**：已确认 / 高概率 / 待确认
5. **崩溃主要源信息速览（结论正下方）**：① 日志结尾原文（约 30~50 行含 fatal/signal）② gdb `bt` 崩溃线程栈原文
6. **附录 A：gdb 原始信息**（完整命令 + 原始输出，不裁剪）
7. **附录 B：日志关键片段**（原文行 + 时间戳；无则写明「无 logfileurl」）

## 8. 幂等去重与知识沉淀

两层去重，互补：

| 机制 | 键 | 命中效果 | 载体 |
|---|---|---|---|
| **filename 级幂等** | core `filename`（全局唯一） | 完全相同的 core → **直接返回既有报告**，免下载/免 gdb | `analyzed_cores_index.md` |
| **崩溃签名级聚合** | `根因类别 + 关键崩溃帧 + 涉事类名` | filename 不同但根因相同 → **命中次数 +1**，沉淀共性 | `crash_patterns.md` |

崩溃签名示例：`GC-UAF | DrainValidated@GarbageCollection.cpp:<行号> | BP_<xxx>_C`。

只归档证据充分（已确认/高概率）的结论；研发修复后回填「修复状态」，便于后续同签名快速判定是否回归。

## 10. 边界与注意事项

- **执行环境**：gdb 分析必须在能访问内网 OSS/日志下载服务与带符号二进制目录的 DS 分析机上；skill 只提供分析指令，不能凭空联网。
- **下载时效**：`coredumpurl` 是 OSS 签名 URL，含 `Expires`，过期即 403 —— 拿到卡片尽快下载，批量时先全量下载再逐个分析。
- **版本一致性**：换 core 可能换版本，务必用对应版本的带符号二进制，否则栈全是 `?? ()`；用 core 头 `Core was generated by '...'` + build-id 交叉核对。
- **精确数值**：时间戳/地址等精确值以 `Read` 读原文为准，Grep 上下文可能截断负号/长数字。
- **防幻觉**：所有崩溃/引用/类型结论必须有 gdb 输出或源码证据支撑；无符号先修环境，别拿垃圾帧下结论。
- **依赖确认**：部署前确认落库工具已就绪、有写表格权限；`ds-coredump-analysis` skill 目录完整拷贝。
