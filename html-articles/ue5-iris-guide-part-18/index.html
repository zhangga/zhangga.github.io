18.0 · Operating Doctrine

从“能跑”到“可运营”

最佳实践不是一组永远正确的 CVar，也不是把所有对象改成 Push Model。它是一套把复制正确性、服务器成本、连接预算、网络劣化和回退能力放在同一张验收表上的工程方法。

LEVEL 01能复制
不等于复制正确
LEVEL 02复制正确
不等于满足预算
LEVEL 03平均值通过
不等于尾延迟通过
LEVEL 04一次通过
不等于可以发布

一套可运营的复制方案，至少要能持续回答四个问题：

SCOPE

谁应该收到？

Owner、Connection、Level、Group、Grid 与 Dynamic Filter 是否让每条连接只看到授权且相关的对象。

DIRTINESS

何时发现变化？

Push 标脏、轮询频率、Dormancy wake 和 Fragment 采集是否覆盖所有真实修改路径。

DELIVERY

何时到达？

优先级、包预算、可靠队列、丢包恢复和依赖是否让关键状态在最大可接受时间内到达。

第四个问题更容易被忽略：如果新配置让 P99 服务器帧、错误率或最大更新年龄恶化，能否在不改客户端协议、不重启全服的前提下停止灰度并恢复上一组配置？没有观测、版本隔离和回退的“优化”，不具备生产意义。

01 · BASELINE冻结构建、场景、人数、网络档位和采集窗口。
02 · ONE LEVER一次只改变 scope、poll、dormancy、delta 或 priority 中的一项。
03 · CAPTURE记录 CPU、对象漏斗、字节、内存和业务断言。
04 · COMPARE比较同场景 P50 / P95 / P99，而不是只看单帧。
05 · BREAK IT加入 lag、jitter、loss、join、travel 与 reconnect。
06 · SHIP满足闸门才灰度；异常触发回退和证据保留。
最危险的反模式：先抄参数，再解释结果

一个项目的 15,000 cm cull distance、30 Hz polling 或 1.0 priority，放到另一个移动速度、武器射程、对象密度和带宽档位不同的项目里，没有任何“最佳”含义。参数必须来自场景约束和测量，不来自截图。

18.0 · Measurement Contract

先建立证据基线，再碰配置

性能优化不是在控制台里寻找让数字变绿的开关。第一步是写一份可重复的场景合同，让修改前后面对同一组输入、同一组统计口径和同一组正确性断言。

场景合同：让两次采集真正可比

维度必须记录为什么常见误判
构建commit、target、config、CVar snapshot开发版、测试版和 Shipping 的统计与检查成本不同拿 Editor 与 Dedicated Server 直接比较
服务器硬件、tick rate、线程、实例密度poll 与 filter 的可用毫秒预算由它决定把空闲开发机结果当云实例容量
负载连接数、机器人比例、Root / SubObject 数CPU 和内存不是只随玩家数线性变化只记录“100 人”，不记录每人可见对象
玩法地图、阶段、移动模式、技能密度大厅、跳伞、缩圈、团战的 dirty 分布完全不同只测出生点静止场景
网络RTT、jitter、loss、bandwidth cap丢包会改变可靠队列、baseline 与收敛时间用零延迟 PIE 证明生产正确
窗口warm-up、capture length、P50/P95/P99短采样会漏掉 join burst 和 GC / travel 峰值用平均值掩盖尾部尖峰
断言owner、proxy、late join、wake、travel性能下降可能来自“少发了本应发送的数据”字节更少就判定优化成功

把复制链压成六层漏斗

01REGISTERED系统跟踪的 Root 与 SubObject
02IN SCOPE本连接通过过滤的对象
03DIRTY变化、重发或初始状态
04SCHEDULED达到优先级候选门槛
05WRITTEN真正进入位流和包预算
06APPLIED远端解析、应用并收敛

每一层都对应不同的问题。Registered 太大，先减少对象和 Fragment；In Scope 太大，先查 Filter；Dirty 太大，先查 Push / Poll 和状态设计；Scheduled 到 Written 掉得多，才去看 prioritization、packet budget 和可靠队列；Written 正常但 Applied 错误，则应检查引用、协议、依赖和接收应用。不要用同一个“网络慢”解释所有层。

四层证据，而不是一个 stat

证据层工具重点观察产出
CPUTiming Insights / Iris CSVPreUpdate、Poll、Filter、Prioritize、Quantize、WriteP95/P99 毫秒与热点调用

-trace=net -NetTrace=1 -tracehost=localhost

# 同一用例还需要记录：
build + map + phase + tick-rate + connections
+ object counts + network profile + capture window
+ gameplay correctness assertions
Verbose 统计本身也有成本

本地 5.7.4 的 net.Iris.UseVerboseIrisCsvStats 在非 Shipping 默认开启、Shipping 默认关闭；UseVeryVerboseIrisCsvStats 会让未显式配置的类型也各自生成统计，源码明确提示会造成显著 CSV 膨胀。诊断构建和容量构建要分开。

18.1 · Change Discovery

Push Model 与轮询：先修正确性，再谈节省

Push Model 的价值是让系统跳过“没有变化却仍被检查”的工作；它不减少真实变化本身，也不会替你找到所有修改点。一个漏标脏的属性看起来极其省 CPU，因为它根本没有被发送。

不是一个开关，而是五道门

GATE 01编译能力WITH_PUSH_MODEL 可用，目标构建包含相关路径。
GATE 02全局启用Net.IsPushModelEnabled 为 true。
GATE 03Iris 模式net.Iris.PushModelMode 允许兼容路径使用 Push。
GATE 04属性声明属性或 Fragment 具备 Push-based dirtiness 契约。
GATE 05修改标脏每条服务端修改路径都在正确对象、正确成员上标脏。
; DefaultEngine.ini — 只是启用条件，不是收益证明
[SystemSettings]
Net.IsPushModelEnabled=1
net.Iris.PushModelMode=2
本地 5.7.4 事实

net.Iris.PushModelMode 的构造默认值为 2，但 LegacyPushModel.cpp 明确要求全局 Push Model 也已启用。ObjectPoller 中的 net.Iris.Poll.FilterOutNonDirtyPushBasedObjects 会在 poll loop 前屏蔽符合条件且未脏的 fully-push 对象；“部分属性 Push”不能自动获得同样的跳过保证。

四种状态，四种发现策略

状态来源推荐起点理由必须防住
统一 setter 的高频状态Push修改入口清晰，可以精确标脏旁路写、数组内部修改、错误 owner
第三方或遗留代码直接写Poll短期内无法证明所有写路径高 PollWaste 和每帧扫描
正在迁移的混合类Hybrid逐属性建立覆盖而不是一次重写误标 fully-push 导致静默丢更新
外部系统生成快照PreUpdate + Push/Poll在安全边界集中生成只读复制状态重复拷贝、跨线程时序、过度标脏

PollFrequency 的单位是“每秒次数”

FObjectReplicationBridgePollConfig::PollFrequency 会根据当前 TickRate 换算成 frame period，最大 frame period 为 255；配置为 0 表示每帧轮询。没有命中类级覆盖的 Actor 通常沿用 NetUpdateFrequency。因此“PollFrequency=10”不是“每 10 帧一次”。

; 起步示例：数字必须由项目场景替换
[/Script/IrisCore.ObjectReplicationBridgeConfig]
+PollConfigs=(ClassName=/Script/MyGame.HighRateProjectile,PollFrequency=30,bIncludeSubclasses=true)
+PollConfigs=(ClassName=/Script/MyGame.WorldPickup,PollFrequency=2,bIncludeSubclasses=true)

; 本地 5.7.4 默认允许这些映射生效
net.Iris.UseFrequencyBasedPolling=1
net.Iris.AllowPollPeriodOverrides=1

正确调频的单位不是“Actor 类型”，而是“最大允许状态年龄”。如果某个状态最多允许 50 ms 过期，那么发现、排队、写入和网络传输共同分享这 50 ms；单纯把 polling 设成 20 Hz 并不保证 50 ms 内到达。反过来，常驻静态招牌即使属于 Actor，也没有理由每帧检查。

Push / Poll 上线指标

WASTE

轮询浪费

PollCount、PollWasteCount、PollWasteMS，以及每类对象的无变化检查比例。

COVERAGE

标脏覆盖

setter 路径审计、开发构建断言、owner / proxy 值对比和 late join 完整状态。

AGE

最大状态年龄

从服务端修改到目标连接应用的 P95 / P99，而不只看平均更新率。

大纲中的“10 倍提升”应改写为实验问题：在同构建、同场景、同连接数下，fully-push 对象让 PollWaste、服务器帧和最大状态年龄分别变化了多少？
18.1 · Idle State & Baselines

Dormancy 与 Delta：一个省检查，一个省位流

Dormancy 解决“对象长时间不变，为什么还要进入常规轮询”；Delta Compression 解决“对象确实要发，为什么每次都发完整状态”。两者作用在不同阶段，也各自带着必须验证的生命周期成本。

Dormancy 是显式状态机

AWAKE常规 poll / push 路径
REQUEST请求进入 dormant
FINAL STATE最后状态有发送机会
FILTER POLL常规轮询集合剔除
MUTATION玩法再次改变状态
FLUSH / WAKE强制 poll 并恢复收敛

本地 5.7.4 中，Actor 的 NetDormancy 变化经 FReplicationSystemUtil::NotifyActorDormancyChange 进入 UObjectReplicationBridge::SetObjectWantsToBeDormant；net.Iris.UseDormancyToFilterPolling 默认开启，用 bitset 把 dormant 对象从常规 poll 集合中剔除。FlushNetDormancy 则通过 NetFlushDormantObject 请求一次强制更新。

// 方向示例：先唤醒，再修改，再标脏
void AWorldChest::SetOpened(bool bNewOpened)
{
    if (bOpened == bNewOpened)
    {
        return;
    }

    FlushNetDormancy();
    bOpened = bNewOpened;
    MARK_PROPERTY_DIRTY_FROM_NAME(AWorldChest, bOpened, this);
}
Dormant RPC 不能替代属性生命周期

本地还有 net.Iris.RPC.AllowOnDormantObjects 与 net.Iris.RPC.AutoNetFlushOnDormantObjects。它们控制 dormant object 上 RPC 的允许与自动 flush 行为，但不应成为“忘记唤醒属性也没关系”的设计依据。Root 与 SubObject、DORM_Initial、late join 和 RPC 丢失策略都要单独测试。

Delta Compression 的三栏账本

节省什么

长寿命对象重复发送大状态时，只写相对已确认 baseline 的变化，减少 state bits。

增加什么

逐连接 baseline、change mask、确认状态、失效管理和额外内存。

怕什么

丢包、role / condition 变化、baseline 失效、短命对象和尚未摊薄的首次状态。

; 类级允许；并不保证这个类一定得到正收益
[/Script/IrisCore.ObjectReplicationBridgeConfig]
+DeltaCompressionConfigs=(ClassName=/Script/MyGame.LongLivedReplicatedState,bEnableDeltaCompression=true)

; 本地 5.7.4 全局开关与 baseline 节流默认
net.Iris.EnableDeltaCompression=1
net.Iris.MinimumNumberOfFramesBetweenBaselines=60
对象形态Delta 候选性先看指标反例
长寿命、大状态、局部变化高bits/update、baseline hit、memory每次几乎全字段改变
短命投射物低initial state 与生命周期尚未建立有效 baseline 就销毁
PlayerState按项目验证每连接状态、role / owner 转换条件变化导致 baseline 频繁失效
大数组需分解change mask、元素 churn、丢包数组重排让 delta 失去局部性
推荐顺序：先减少 scope，再减少 polling；静止对象使用 dormancy，仍然昂贵的长寿命状态才进入 delta A/B。压缩不相关对象，是在更高成本地发送不该发送的数据。
18.2 · Scope Architecture

过滤漏斗：只让该发的对象进入热路径

过滤的第一原则不是“半径设多大”，而是把规则放进成本最低、变化最少、最容易证明正确的那一层。稳定的业务事件应该更新 Connection 或 Group；空间问题交给 Grid；只有对象 × 连接规则频繁变化时，才考虑 Dynamic Filter。

关卡流送不是一份虚构的 Filter 配置

本地 UEngineReplicationBridge 会为关卡创建 Group，把 Root Object 加入对应 Level Group，再由 UNetDriver 根据连接的关卡可见状态更新过滤状态。它还处理 Actor 运行时换 Level、Persistent Level、Seamless Travel 和 PlayerController 特例。

CREATE

关卡出现

创建或取得 Level Group，并维护唯一名称与生命周期。

MEMBERSHIP

对象归组

Root Object 随所属 Level 加入或迁移 Group，SubObject 跟随 Root 语义。

CONNECTION

连接可见

NetDriver 更新每条连接的 Group FilterStatus，关卡未加载时排除对象。

因此正确的验证不是“有没有打开 Level Filter CVar”，而是：客户端何时声明 Level ready、Group status 何时变化、Actor 换 Level 后旧 membership 是否移除，以及 travel / unload / late join 时对象是否按预期创建和销毁。

Group 优先表达稳定业务规则

队伍、频道、副本、观战权限和阶段门禁通常由离散事件改变。用 Group 把这些事件转换为 membership 和 per-connection status，系统只在事件发生时更新；如果把同样逻辑放进 Dynamic Filter，就会在每轮对每条连接重新计算。

// 公共 API 方向：错误处理和生命周期由项目补全
FNetObjectGroupHandle TeamGroup =
    ReplicationSystem->CreateGroup(TEXT("Team.Red"));

ReplicationSystem->AddExclusionFilterGroup(TeamGroup);
ReplicationSystem->AddToGroup(TeamGroup, ObjectHandle);

ReplicationSystem->SetGroupFilterStatus(
    TeamGroup,
    ConnectionId,
    ENetFilterStatus::Allow);

Dynamic Filter 仍有价值，但它是最后手段：一个对象同时只能分配一个 Dynamic Filter；它在 Connection 和 Group 之后执行，无法把已经排除的对象“复活”；热路径需要使用缓存、SoA、bit array 和连续批次，不能逐对象做 UObject 查找、射线检测或容器分配。

18.3 · Case Blueprint

案例不是答案，而是一套评审模板

下面四个案例不会给出“一键复制”的 DefaultEngine.ini。每个案例都用同一张蓝图审查负载、scope、变化发现、排序、位流、网络劣化和回退，让项目团队能替换输入，而不是继承隐含假设。

01 · LOAD SHAPE连接数不是唯一规模；还要记录同一 AOI、Root / SubObject、dirty ratio 和峰值阶段。
02 · SCOPE哪些对象必须全局、按 owner、按 group、按 level 或按 grid 可见。
03 · CHANGE状态由 setter、物理、AI、外部系统还是遗留代码修改，能否证明 Push 覆盖。
04 · SCHEDULE哪些对象的最大状态年龄最短，哪些只需最终进展，如何防止饥饿。
05 · PAYLOAD用 NetTrace 实测 bytes/update、RPC、NetBlob、exports 和 resend，而不是猜结构大小。
06 · FAILURE在 loss、lag、join、travel、reconnect 与 owner change 下如何证明收敛并回退。

每个参数都要带三件东西

INPUT为什么从这个值开始
METRIC它应该改变哪条曲线
BOUNDARY什么条件下不再成立
ROLLBACK恶化时恢复什么

例如，把 NPC PollFrequency 从 10 Hz 降到 2 Hz，不是因为“开放世界 NPC 应该 2 Hz”，而是因为远端表现允许更大的状态年龄；验收要看 PollWaste 与远端动画／位置最大年龄；进入战斗时必须升级 tier；回退则恢复旧 class mapping 或关闭 cohort 配置。

18.3 · Case 01

206 kbps 不是线路预算

18.4 · Migration

从传统系统迁移：五阶段跑道

迁移不是把 net.Iris.UseIrisReplication 从 0 改成 1。可靠的路径先清点隐式依赖，再建立双路径正确性，最后才做性能对比和生产灰度。

Inventory清点 relevancy、priority、ReplicationGraph、SubObject、NetSerialize、RPC、Dormancy 与 Push。EXIT · 所有隐式扩展点有 owner
Shadow测试分支启用 Iris，冻结场景合同，保留 legacy 结果作为 oracle。EXIT · 两条路径可重复采集
Correctness先修 registered subobject、Filter、Serializer、Owner、Role 与生命周期。EXIT · 劣化网络下断言通过
Performance同负载比较 CPU、scope、dirty、bits、memory、max age 与 join burst。EXIT · 预算和回归阈值达标
Rollout按 fleet、地图或 playlist 灰度，监控 protocol、P99、错误率并演练回退。EXIT · 全量且回退窗口关闭

传统扩展点不能原样带过去

传统路径Iris 对应迁移动作验收重点
IsNetRelevantForFiltering拆出 owner、group、level、spatial 与动态规则每连接真值矩阵

Iris 要求 Registered SubObject List

本地 UEngineReplicationBridge 会确保 GDefaultUseSubObjectReplicationList 已启用，并给出 net.SubObjects.DefaultUseSubObjectReplicationList=1 提示。非 Actor / ActorComponent 的 UObject 还要正确实现 RegisterReplicationFragments。这属于正确性门，不应拖到性能阶段。

灰度单位要能隔离协议和玩法风险

优先按服务器 fleet、地图、playlist 或内部 cohort 灰度，而不是随机把同一协议会话的一半对象切换实现。Dashboard 至少按 engine build、game commit、config hash、map、mode 和 cohort 切片。回退条件在发布前写好：protocol mismatch、正确性断言、server frame P99、max state age、disconnect 和 join failure 任一越线即停止扩大。

18.5 · Release Control

发布闸门：PASS、WATCH、BLOCK

上线检查表不是“我们看过了”，而是每一项都有场景、指标、阈值、证据链接和负责人。任何 BLOCK 都停止扩大；WATCH 必须有时间窗口和自动回退；PASS 也要能在下一个版本继续复现。
