THE REAL SWITCH

配置不是参数表，而是一份启动契约

很多项目第一次接入 Iris 时，会把问题简化成“把 net.Iris.UseIrisReplication 设为 1”。但 UE 5.7.4 真正做决定的时刻，是 UEngine::CreateNetDriver_Local 创建 NetDriver 时。

在那个时刻，引擎同时检查：Iris 代码是否可见、插件模块是否已经加载、这个 NetDriver 是否被允许使用 Iris、当前策略要求哪套复制系统，以及最终能否构造 Replication Bridge 和 ReplicationSystem。任何一环失败，结果都可能是 Legacy / Generic Replication System，或者创建了 NetDriver 却没有可工作的 Iris 实例。

编译可见

模块能包含 Iris API，宏和 IrisCore 依赖已准备。

插件装载

Iris Runtime 模块启动，并把 IrisCore 加入运行时。

能力许可

目标 NetDriver 命中 bCanUseIris=true 的配置。

策略选择

CVar、GameMode、PIE 与命令行得出最终选择。

实例创建

Bridge、ReplicationSystem 和 RepSystemId 真正建立。

代码可见∧模块已加载∧Driver 获准∧策略选 Iris→使用 Iris
最重要的边界：CVar 不是热切换器

运行中把 net.Iris.UseIrisReplication 从 0 改成 1，只会影响之后参与选择的新 NetDriver。它不会把已经存在、已有连接的 NetDriver 原地改造成 Iris。无缝旅行通常复用现有 NetDriver，因此也不能把 GameMode 改值当作旅行中的热迁移方案。

因此，本篇不从“参数解释”开始，而从“这份配置在什么时候被谁读取、最终创建了哪个实例”开始。只要把配置与生命周期绑定，绝大多数“配置看着对、运行却不对”的问题都会变成可定位的条件判断。

FIVE LAYERS

五层控制面：每一层回答不同问题

Iris 的配置分散在项目描述符、Build Rules、Engine.ini、GameMode / GameInstance 和 NetDriver 实例中。它们不是重复开关，而是五个不同层级。

层回答的问题UE 5.7.4 入口失败表现
编译层Gameplay 模块能否调用 Iris API？SetupIrisSupport(Target)Header、宏或链接符号不可见
插件层运行时是否加载 IrisCore？Iris.uplugin、FIrisModule选择 Iris 后因模块未加载而回退
能力层某个 NetDriver 是否允许 Iris？FIrisNetDriverConfig即使命令行强制 1，也仍使用 Generic
策略层这一次创建希望使用哪套系统？CVar、GameMode、GameInstance、PIE、命令行不同环境选择结果不一致
实例层创建出的系统容量和行为是什么？FNetDriverReplicationSystemConfig 与配置 CDO容量不足、映射无效或性能不合预期

能不能

POLICY

想不想

全局 CVar 是默认偏好；GameMode / GameInstance 和命令行可以改变某次创建。

INSTANCE

实际是什么

最终以 NetDriver 的 IsUsingIrisReplication()、创建日志和 RepSystemId 为证。

变更安全生效点是否建议热改

PRECEDENCE

NetDriver 到底怎样选择 Iris

UEngine::WillNetDriverUseIris 是 UE 5.7.4 的核心裁决点。它先判断资格，再叠加默认偏好、场景覆盖和命令行，最后检查模块。

01
NetDriver 能力许可从 IrisNetDriverConfigs 查 bCanUseIris
没有许可，后面任何“选 Iris”都不能越过
02
引擎默认偏好ShouldUseIrisReplication() 读取全局 CVar
初始结果 = capability ∧ default policy
03
GameInstance / GameModeGetDesiredReplicationSystem()
Generic 可关闭；Iris 仍需 capability
04
PIE 服务器跟随Dedicated Server PIE 的客户端 GameNetDriver 跟随服务端
只在特定 PIE 条件下介入
05
命令行最终覆盖-UseIrisReplication=1 或 0
1 仍受 capability 限制；0 强制 Generic
06
IrisCore 模块检查FModuleManager::IsModuleLoaded("IrisCore")
模块没加载，最终不能使用 Iris

IrisNetDriverConfigs 自己也有匹配优先级

FIRSTNetDriverName

精确匹配具体命名实例，例如 GameNetDriver。

SECONDWildcard Name

例如 UnitTestNetDriver*，匹配一组命名实例。

THIRDDefinition

匹配 GameNetDriver、BeaconNetDriver 等定义。

NONE无匹配

bConfigCanUseIris=false，默认没有 Iris 资格。

[/Script/Engine.Engine] ; 最高优先级：精确命名实例 +IrisNetDriverConfigs=(NetDriverName="MyGameNetDriver",bCanUseIris=true) ; 第二优先级：通配命名实例 +IrisNetDriverConfigs=(NetDriverWildcardName="SecondaryNetDriver*",bCanUseIris=true) ; 第三优先级：NetDriverDefinition +IrisNetDriverConfigs=(NetDriverDefinition=GameNetDriver,bCanUseIris=true) +IrisNetDriverConfigs=(NetDriverName=DemoNetDriver,bCanUseIris=false)
“混合模式”是每个 NetDriver 选择，不是每个 Actor 选择

同一进程中可以让 GameNetDriver 用 Iris、DemoNetDriver 用 Generic；也可以让不同进程或服务器池使用不同系统。但同一个 NetDriver 里不能让一部分 Actor 由 Iris 复制、另一部分 Actor 由 Legacy 复制。Replication Graph 与 Iris 也不能同时驱动同一个 NetDriver。

16.1 · ENABLE IRIS

UE 5.7.4 中正确启用 Iris

推荐把“编译、装载、资格、默认策略”都显式写进工程。这样 Local、CI、Dedicated Server 和回退流程看到的是同一份意图。

第一步：启用 Iris 插件

本地 UE 5.7.4 的插件仍位于 Engine/Plugins/Experimental/Iris/。描述符中 EnabledByDefault=false、IsBetaVersion=true，因此项目应显式启用：

{ "Plugins": [ { "Name": "Iris", "Enabled": true } ] }

第二步：让 Gameplay 模块拥有 Iris 依赖

如果游戏模块直接包含 Iris Header 或调用 Iris API，在模块的 *.Build.cs 中调用：

public class MyGame : ModuleRules { public MyGame(ReadOnlyTargetRules Target) : base(Target) { SetupIrisSupport(Target); } }

在这份 UE 5.7.4 源码中，SetupIrisSupport 会加入 UE_NET_HAS_IRIS_FASTARRAY_BINDING=1、UE_WITH_IRIS=1 和 IrisCore 依赖。这里不照搬其他版本可能出现的 TargetRules.bUseIris 步骤，因为本地 5.7.4 的 TargetRules 并没有这项配置。

第三步：写清 NetDriver 资格与默认策略

[/Script/Engine.Engine] +IrisNetDriverConfigs=(NetDriverDefinition=GameNetDriver,bCanUseIris=true) [SystemSettings] ; Iris 的注册式 SubObject 迁移前置条件 net.SubObjects.DefaultUseSubObjectReplicationList=1 ; 让之后创建且获准的 NetDriver 默认选择 Iris net.Iris.UseIrisReplication=1

引擎 BaseEngine.ini 已为 GameNetDriver 提供 bCanUseIris=true，并让 DemoNetDriver 不使用 Iris。项目里显式写出 GameNetDriver 的目的，是固定项目意图，也提醒团队：一旦项目用数组清理语法覆盖基础数组，就必须重新补齐需要的资格项。

三种策略入口

PROJECT DEFAULT

配置文件

适合项目稳定默认。随进程启动加载，在创建 NetDriver 前就绪。

net.Iris.UseIrisReplication=1
CI / ROLLBACK

命令行

适合 A/B、自动化矩阵和紧急回退，具有最终策略覆盖权。

-UseIrisReplication=1|0
CONTROLLED TEST

控制台 / C++

只在创建新 NetDriver 前改变默认。已有 Driver 不会被热切换。

IrisCore 模块加载：开关生效之前发生了什么

插件描述符只声明一个名为 Iris 的 Runtime 模块。真正的基础设施位于 IrisCore，由 Iris 模块在启动时加载。

FIrisCoreModule 特意在启动早期解析 -UseIrisReplication，因为 NetDriver 的选择也发生在初始化期。模块还会跟踪运行中的 ReplicationSystem 数量：如果有活跃系统后又加载了可能注册多态网络类型的新模块，源码会警告建议重启 ReplicationSystem 或 NetDriver，以避免协议注册时序带来的风险。

为什么“插件已勾选”仍然不等于“正在使用 Iris”

插件启用只能保证 IrisCore 有机会被加载。某个 NetDriver 仍要命中 bCanUseIris=true，并在创建时由策略选择 Iris。验证时要看 NetDriver 和 ReplicationSystem 实例，而不是只看 Plugins 面板。

16.2 · CONFIG OBJECTS

配置对象地图：定义、映射、参数

Iris 的 Filter 和 Prioritizer 配置最容易出错，因为同一个行为跨越三个配置层：先注册名字，再把 Gameplay 类映射到名字，最后配置实现类的算法参数。

名字注册

  • NetObjectFilterDefinitions
  • NetObjectPrioritizerDefinitions
  • 名字 → 实现类 → ConfigClass
  • 系统初始化时创建有效实现

Gameplay 类映射

  • ObjectReplicationBridgeConfig
  • Poll / Filter / Prioritizer
  • Delta / Critical Class
  • 继承树决定覆盖关系

算法参数

  • NetObjectGridFilterConfig
  • Sphere / FOV / Count Limiter
  • ReplicationFilteringConfig
  • 半径、Cell、帧数、优先级

例如，下面三段分别完成“注册 Spatial 名字”“让 Pickup 使用 Spatial”“给 Spatial 使用的 Grid 实现配置数值”。缺任意一段，行为都可能与预期不同：

[/Script/IrisCore.NetObjectFilterDefinitions] +NetObjectFilterDefinitions=(FilterName=Spatial,ClassName=/Script/IrisCore.NetObjectGridWorldLocFilter,ConfigClassName=/Script/IrisCore.NetObjectGridFilterConfig) [/Script/IrisCore.ObjectReplicationBridgeConfig] +FilterConfigs=(ClassName=/Script/MyGame.MyPickup,DynamicFilterName=Spatial,FilterProfile=StablePickup) [/Script/IrisCore.NetObjectGridFilterConfig] CellSizeX=12000 CellSizeY=12000 DefaultCullDistance=12000 +FilterProfiles=(FilterProfileName=StablePickup,FrameCountBeforeCulling=8)

UObjectReplicationBridgeConfig 是类策略中枢

字段用途主要边界
PollConfigs按类覆盖非 Push 状态的轮询频率更深子类优先；Actor / Object 禁止
FilterConfigs按类分配 Dynamic Filter 与 ProfileFilterName 必须先注册
PrioritizerConfigs按类分配动态 Prioritizer固定优先级实例会忽略类映射
DeltaCompressionConfigs按类和继承树打开 / 关闭 Delta还受全局开关、容量、Baseline 限制
CriticalClassConfigs协议不匹配时决定是否断开适合真正无法继续的关键类
DefaultSpatialFilterName需要空间过滤但无显式类映射时的默认 Filter基础配置默认是 Spatial
RequiredNetDriverChannelClassName对象复制所需的 Channel 类基础配置为 DataStreamChannel
配置 CDO 不是热更新承诺

这些类是 config=Engine 的 transient UObject，Bridge 和 ReplicationSystem 在初始化时读取它们。开发时修改 ini 后，最稳妥的验证方式是结束并重建网络会话；不要假设已有实例的类树缓存、Filter、Prioritizer 和 Delta 映射都会被完整刷新。

POLL CONFIG

轮询频率：从“每秒次数”落到帧周期

Iris 希望尽可能使用 Push Model，但仍支持轮询。对没有可靠脏标记的对象，PollConfigs 决定多长时间检查一次 Gameplay 状态。

[/Script/IrisCore.ObjectReplicationBridgeConfig] ; 每帧轮询：PollFrequency=0 +PollConfigs=(ClassName=/Script/MyGame.MyProjectile,PollFrequency=0,bIncludeSubclasses=true) ; 30 次/秒，具体帧周期依赖 MaxTickRate +PollConfigs=(ClassName=/Script/MyGame.MyCharacter,PollFrequency=30,bIncludeSubclasses=true) ; NPC 10 次/秒；某个 Boss 子类可再写更具体覆盖 +PollConfigs=(ClassName=/Script/MyGame.MyNPC,PollFrequency=10,bIncludeSubclasses=true) ; 静态交互物 2 次/秒 +PollConfigs=(ClassName=/Script/MyGame.MyWorldItem,PollFrequency=2,bIncludeSubclasses=true)

源码怎样换算

UObjectReplicationBridge::ConvertPollFrequencyIntoFrames 使用当前 MaxTickRate 将频率换成帧间隔，并限制在 uint8 能表达的 0～255。PollFrequency <= 0 返回 0，即每帧可轮询。

MaxTickRate÷PollFrequency−1→Clamp 0..255→PollFramePeriod

这意味着 PollFrequency 不是独立的高精度墙钟定时器，而是网络 Tick 的帧调度输入。服务器 TickRate 改变后，同一配置对应的帧间隔会重新解释。上限 255 帧在 30Hz 下大约是 8.5 秒量级。

类继承与禁止项

DEEPER WINS

更具体类优先

父类配置可以覆盖整棵树；更深子类的条目会替换更通用的频率。

FORBIDDEN

不要配置 Actor / Object

源码明确禁止把最顶层 Actor 或 Object 作为轮询覆盖类名，以避免全局性能灾难。

SUBOBJECT

SubObject 跟随 Root

Bridge 会安排 SubObject 与 Root Object 在同一帧轮询，避免父子状态错开。

Push Model 与 Poll 的正确关系

Push Model 正确标脏时，Iris 不需要持续扫描每个成员；没有 Push 支持的对象会按 NetUpdateFrequency 或类覆盖频率轮询。net.Iris.AllowPollPeriodOverrides 默认允许 Bridge 配置覆盖，net.Iris.UseFrequencyBasedPolling 默认启用频率调度。

降低 PollFrequency 不是免费优化

它减少检查次数，也扩大“Gameplay 值已改变、Iris 尚未观察到”的最长窗口。先用 Part 15 的 Poll Count / Poll Waste 判断扫描浪费，再用延迟指标确认降频不会破坏玩法响应。对于完全 Push 的关键类，优先修正脏标记，而不是靠每帧 Poll 掩盖漏标。

FILTER & PRIORITY

过滤与优先级：先决定“能否进入”，再决定“先发谁”

Filter 减少每条连接的候选集，Prioritizer 在候选集中分配发送机会。两个系统都以“名字注册 + 类映射”的方式接入，但不能互相替代。

Filter：注册、映射与 Profile

[/Script/IrisCore.NetObjectFilterDefinitions] ; BaseEngine.ini 已有这两项；项目通常无需重复 +NetObjectFilterDefinitions=(FilterName=Spatial,ClassName=/Script/IrisCore.NetObjectGridWorldLocFilter,ConfigClassName=/Script/IrisCore.NetObjectGridFilterConfig) +NetObjectFilterDefinitions=(FilterName=NotRouted,ClassName=/Script/IrisCore.FilterOutNetObjectFilter,ConfigClassName=/Script/IrisCore.FilterOutNetObjectFilterConfig) [/Script/IrisCore.ObjectReplicationBridgeConfig] +FilterConfigs=(ClassName=/Script/MyGame.MyPickup,DynamicFilterName=Spatial,FilterProfile=StablePickup) +FilterConfigs=(ClassName=/Script/MyGame.MyServerOnlyInfo,DynamicFilterName=NotRouted) +FilterConfigs=(ClassName=/Script/MyGame.MyGlobalInfo,DynamicFilterName=None)
DynamicFilterName含义不要误解为
Spatial按 Grid / 距离和连接 View 计算相关性对象一定会在 CullDistance 内每帧发送
NotRouted由 FilterOut 实现排除该类对象销毁对象或停止 Gameplay 生命周期
None不为该类分配 Dynamic Filter绕过 Owner、Group、Connection 等全部规则
自定义名字使用 Definitions 注册的实现和 ConfigClass只写名字就能自动找到任意 C++ 类

bForceEnableOnAllInstances=true 会要求类映射在实例具有 bAlwaysRelevant 或 bOnlyRelevantToOwner 等设置时仍强制使用。只有当团队清楚这些实例语义为何需要被覆盖时才启用。

Prioritizer：默认空间算法与专用算法

[/Script/IrisCore.NetObjectPrioritizerDefinitions] +NetObjectPrioritizerDefinitions=(PrioritizerName=FPSOwnerBoost,ClassName=/Script/IrisCore.SphereWithOwnerBoostNetObjectPrioritizer,ConfigClassName=/Script/IrisCore.SphereWithOwnerBoostNetObjectPrioritizerConfig) +NetObjectPrioritizerDefinitions=(PrioritizerName=RacingFOV,ClassName=/Script/IrisCore.FieldOfViewNetObjectPrioritizer,ConfigClassName=/Script/IrisCore.FieldOfViewNetObjectPrioritizerConfig) [/Script/IrisCore.ObjectReplicationBridgeConfig] +PrioritizerConfigs=(ClassName=/Script/MyGame.MyCharacter,PrioritizerName=FPSOwnerBoost) +PrioritizerConfigs=(ClassName=/Script/MyGame.MyRaceVehicle,PrioritizerName=RacingFOV) +PrioritizerConfigs=(ClassName=/Script/MyGame.MyWorldItem,PrioritizerName=Default)
实现决策依据适合场景
Sphere距各 View 的内外半径与线性插值通用三维世界位置对象
SphereWithOwnerBoostSphere 结果 + 对 owning connection 的加成玩家控制对象、Owned 装备
FieldOfView内外球、前方视锥、视线胶囊取最大值高速前向运动、竞速
NetObjectCountLimiter每次只考虑固定数量，RoundRobin 或 FillPlayerState、低频大集合
第一条有效 Prioritizer 定义具有特殊地位

UNetObjectPrioritizerDefinitions 会把第一条有效定义当作默认空间 Prioritizer。UE 5.7.4 的基础配置先注册 DefaultPrioritizer 对应 Sphere。项目追加专用实现时不要无意清空并改变这条顺序。

优先级会跨网络 Tick 累积。0.2 并不表示“只有 20% 数据会发送”，而表示当对象处于该区域时，优先级以较慢速度到达考虑阈值。提高某类优先级只改变预算内的先后顺序，不会凭空增加总带宽。

DELTA · GRID · DESCRIPTOR

这些配置都能改变网络结果，但作用层完全不同：Grid 决定空间候选，Hysteresis 防止边界抖动，Delta 改变状态编码，Descriptor 配置约束协议构建。

多进程 PIE 很直观；单进程多 World PIE 更容易误判，因为服务器和多个客户端共享进程，却各自拥有 World、NetDriver、Bridge 与 ReplicationSystem。

FReplicationSystemFactory 在进程级数组中寻找第一个空槽，以数组索引作为 ReplicationSystemId。销毁系统后空槽可以复用。因此图中的 0、1、2 只是一次启动的常见示例，不是“服务器永远为 0、Client 1 永远为 1”的持久约定。

为什么 NetRefHandle 需要系统 ID

UE 5.7.4 的 FNetRefHandle 为 ReplicationSystemId 保留 10 bit。完整句柄同时包含对象 ID 与系统 ID，这样同一进程中不同 PIE World 即使分配出相同对象 ID，也不会被当成同一个完整句柄。源码注释直接指出：PIE 时要追踪句柄所属实例。

Dedicated Server PIE 的跟随规则

当当前 Context 是 PIE、不是 Dedicated、目标是 GameNetDriver 时，WillNetDriverUseIris 会查找 PIE instance 0；如果它以 Dedicated Server 运行，就让客户端 GameNetDriver 跟随服务器实际选择的复制系统。这避免服务器使用 Iris、PIE 客户端却按本地默认走 Generic。随后命令行仍有最终覆盖权，因此测试矩阵要保持所有进程参数一致。

16.6 · MIGRATION & OPERATIONS

五阶段迁移、故障矩阵与上线检查

成熟的迁移不是“某天把默认 CVar 改成 1”，而是先建立 Legacy 基线，再让 Iris 和 Generic 都能启动，逐步修正兼容性、配置性能，最后演练默认启用与回退。

本篇结论

CONTRACT

五道门

代码、模块、资格、策略、实例必须同时成立，开一个 CVar 不能替代整条契约。

LAYERS

三层配置

名字注册、Gameplay 类映射、算法参数分层验证，避免“有名字没实现”或“有参数没对象”。

OPERATE

可回退迁移

按 NetDriver / 进程做双路启动，使用同一证据链比较，回退靠重建会话而不是热切换。

工程化接入 Iris 的完成标志，不是配置文件里出现了多少参数，而是团队能证明：哪个 NetDriver 为什么选择 Iris、创建了哪个 RepSystem、每条类映射何时生效，以及怎样安全回退。
