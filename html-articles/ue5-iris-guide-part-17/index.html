SOURCE VERIFIED
17.0 · THE NARROWEST SEAM

为什么需要“高级定制”？

Iris 提供 Filter、Prioritizer、NetSerializer、ReplicationFragment、Bridge 和 DataStream 等多个扩展面。它们不是一套要全部实现的“高级套餐”，而是一组成本相差很大的工具。真正成熟的做法，是先证明内置机制不能表达需求，再进入最窄的一层。

高级不是代码更深，而是边界更清楚：你只替换必须替换的那一小段，其余路径继续交给引擎。

从“买成品”到“改结构”

把网络复制想成装修：改配色和家具对应调配置；移动一面非承重墙对应写 Filter 或 Prioritizer；重新设计水电和承重结构才对应 Fragment、Bridge 或 DataStream。越向下，能力越强，协议兼容、内存布局、生命周期和版本升级成本也越高。

L0
配置内置机制Grid、Owner、Sphere、FOV、Poll、Delta
成本最低；先调参和度量。
L1
Connection / Group / Static Priority固定受众、队伍、频道、常量优先级
事件驱动；通常比动态策略便宜。
L2
自定义 Dynamic Filter对象 × 连接的高频可见性规则
每连接运行；CPU 风险明显。
L3
自定义 Prioritizer项目特有的候选排序与保底策略
要防尺度失控与对象饥饿。
L4
NetSerializer / Fragment特殊值编码、采集、应用与回调
进入协议、量化和 GC 边界。
L5
Bridge / DataStream非标准对象生命周期或传输语义
引擎级维护；升级审计最重。

→

只想调整“先发谁”？ 对象仍应对该连接可见。

Static / Dynamic Prioritizer

Dynamic Filter 是最后手段，不是“比 Group 更高级”的默认选择

Epic 官方文档明确提示：动态 Filter 会持续运行，CPU 成本显著高于 Connection / Group Filter；而且一个对象同一时间只能设置一个动态 Filter。先把能事件驱动的规则移出每连接热路径。

CONTRACTS BEFORE CODE

三个扩展点，一条发送管线

Filter、Prioritizer 和 Fragment 经常被并列介绍，但它们处理的是不同问题、出现在不同阶段。先把三者放回发送管线，后续每个接口的职责就会变得清楚。

SET MEMBERSHIP

Filter

回答“这个对象能不能发给这个连接”。输出的是允许集合，不是排序分数。

ORDER CANDIDATES

Prioritizer

回答“有资格、有变化的对象先发谁”。改变竞争顺序，不改变相关性。

MOVE STATE

Fragment

回答“Gameplay 状态如何进入和离开复制系统”，包括采集、应用与回调。

Connection / Group用事件驱动规则先削减 scope。
Dynamic Filter对剩余对象做连接相关判断。
Dirty / Resend只保留有变化或需要重发的对象。
Prioritizer为本连接批量计算或抬高分数。
Budget带宽、包窗口、依赖共同裁决。
Fragment采集、量化、写入；接收端反向应用。
一条不可逆的推论

对象一旦被 Connection、Group 或 Dynamic Filter 排除，后面的 Prioritizer 再给多高分也不能把它“救回来”。相反，Filter 允许对象也不代表它本帧一定发送；它还必须有可发送变化，并通过预算与依赖检查。

17.1A · DYNAMIC FILTER CONTRACT

Filter 不是逐 Actor 回调，而是批处理门禁

传统相关性代码容易形成“给我一个 Actor 和 Viewer，我返回 true / false”的心智模型。Iris 的动态 Filter 接口刻意换成对象索引、bit array、连接视图和批次，目的是让相同工作在连续内存上完成。

生命周期不是只有 Filter()

OnInit保存配置，按 absolute / current max 分配结构，声明 Traits。
Add Connection建立连接级缓存；Remove 时对称清理。
Add Object验证协议，分配小索引；失败返回 false。
Update Objects只为变化对象刷新可复用快照。
PreFilter每轮过滤前一次性准备跨连接公共数据。
Filter按连接、按批次设置允许位；同一连接可能多次调用。
PostFilter释放本轮临时状态或提交统计。
Remove Object回收 AddObject 创建的索引和缓存。
OnDeinit断开系统引用，清理所有持久资源。
OutAllowedObjects 进来时内容未定义

Filter 必须为自己负责的对象完整写出结果。不能假定数组默认全 0，也不能只“设置允许位”却忘记清除上一次批次的残留。引擎只关心分配给该 Filter 的对象，但实现仍要明确初始化自己的输出。

五组参数各自解决什么

类型重要字段正确用途常见误用
FNetObjectFilterInitParamsReplicationSystem、Config、三种容量建立容量上限和配置引用把 CurrentMax 当成永不增长的绝对上限
FNetObjectFilteringInfouint16 Data[4]保存小索引、偏移或 flags塞大型 gameplay 状态或未管理的裸指针
FNetObjectFilterAddObjectParamsProtocol、InstanceProtocol、StateBuffer、ProfileName定位 RepTag / Descriptor，并建立缓存索引把量化 StateBuffer 直接转成 gameplay struct
FNetObjectFilterUpdateParamsObjectIndices、ObjectCount、FilteringInfos批量刷新变化对象的快照无差别重新扫描全部对象
FNetObjectFilteringParamsOutAllowedObjects、ConnectionId、View、GroupFilteredOutObjects在连接上下文中写允许集合忽略多 View，或试图放回 Group 已排除对象

两个 Traits 决定额外调用

ENetFilterTraits

Spatial

声明该 Filter 按对象 WorldLocation 工作。空间 Filter 仍需维护位置、边界与移动更新，Trait 不是算法本身。

ENetFilterTraits

NeedsUpdate

要求系统为脏对象调用 UpdateObjects。没有该 Trait，就不要期待更新回调为缓存刷新。

GROWTH CONTRACT

Max Index Grow

OnMaxInternalNetRefIndexIncreased 是容量增长契约；所有按 ObjectIndex 索引的数组都要同步扩容。

17.1B · STEALTH AS A SET PROBLEM

手把手建模：隐身系统过滤器

隐身不是一个布尔值，而是“对象、连接、队伍、侦测与观战策略”的关系。直接在 Filter() 里问 Gameplay 世界会把这段关系变成每连接、每对象的昂贵查询；先把它转成集合，算法才会稳定。

第一步：写清可见性矩阵

对象状态Owner队友敌方已侦测敌方未侦测观战连接
普通允许允许允许允许按观战策略
隐身允许允许允许禁止按权限策略
隐藏调试对象按权限按权限禁止禁止管理员可见
“已侦测”必须来自服务器权威状态

客户端可以上报瞄准、视线或能力输入，但不能直接宣布“我看见了这个隐身敌人”。服务器应验证侦测规则，再把结果写入连接可见性快照。Filter 只是执行决策，不是反作弊系统。

FNetObjectFilteringInfo 只有 8 字节，适合保存 VisibilityRecordByObject 的索引；真正的 owner、team 和状态数组放在 Filter 自己维护的 SoA 中。对象移除时回收索引，最大内部索引增长时只扩 ObjectIndex → Record 映射。

第三步：用集合表达规则

第四步：注册 Filter

第五步：把已经复制的对象分配给 Filter

{

    ReplicationSystem->SetFilter(ObjectHandle, StealthHandle);

{

ObjectHandle 必须是已经由 Bridge 开始复制的有效 FNetRefHandle。同一个对象只能有一个 Dynamic Filter；如果“空间 + 隐身”都需要动态逻辑，优先让 Grid 先缩 scope，再评估组合 Filter，或把队伍 / 侦测关系迁移到 Group。

17.1C · HOT PATH DISCIPLINE

Filter 性能：省掉查询，而不是写更聪明的 if

动态 Filter 的规模近似“连接数 × 参与对象数 × 调用频率”。对象判断只省几条分支并不能逆转错误的数据流；真正的收益来自事件驱动、批量快照和连续内存。

PRECOMPUTE

早做一次

在 Gameplay 状态变化时更新权威关系；在 PreFilter 构建本轮连接快照，而不是每个对象重新求解。

BATCH

连续处理

用 SoA、bit array 和复用的 scratch buffer，让 Filter 内层循环只有索引、位运算和简单比较。

MEASURE

按规模验证

分别记录对象数、连接数、每轮更新数、每连接 Filter 时间和 scope 命中率，不只看平均帧。

17.2A · PRIORITY IS NOT PROBABILITY

Prioritizer：不是 0～1 概率，而是累积门槛

大纲里“0.0～1.0”的说法很容易让人以为优先级是归一化概率。UE 5.7.4 的真实契约是：优先级至少为 0；小于 1 时本 tick 不进入候选，达到或超过 1 才有资格；它可以继续大于 1。

1.0 是候选阈值，不是上限；高分是排序信号，不是“本帧必发”的保证。
0 ≤ P < 1

继续积累

本网络 tick 暂不进入复制候选。只要对象未发送，其优先级可以跨 tick 累积。

P ≥ 1

有资格竞争

对象还必须有 dirty state 或 resend 需求；满足阈值不等于一定有数据可发。

AFTER SEND

发送后重置

高分对象仍可能因带宽、包窗口、依赖或其他预算推迟；发送成功后该连接上的累积值重置。

只能抬高已有值，不能随意覆盖

FNetObjectPrioritizationParams 的文档要求实现尊重已经写入的优先级。多个 View、静态值或其他逻辑可能已经提供更高分；自定义 Prioritizer 应使用 Max(existing, calculated)。

UE 5.7.4 契约写法 
for (const uint32 ObjectIndex :
     MakeArrayView(Params.ObjectIndices, Params.ObjectCount))
{
    const float CalculatedPriority =
        FMath::Max(0.0f, CalculatePriority(ObjectIndex, Params));

    Params.Priorities[ObjectIndex] =
        FMath::Max(
            Params.Priorities[ObjectIndex],
            CalculatedPriority);
}

生命周期与 Filter 相似，但输入集合更窄

Init验证 Config，建立 ObjectIndex 到 SoA record 的映射。
Add Object检查 Protocol / RepTag，创建对象级缓存。
Update Objects刷新位置、战斗 flags、owner connection。
PrePrioritize准备本轮公共快照；只调用一次。
Prioritize按连接、按批次处理 dirty / resend 对象。
PostPrioritize汇总统计或释放本轮 scratch。
Remove Object回收 record，清除 owner / flags。
Max Index Grow扩 ObjectIndex 映射，不一定扩 absolute pool。
Deinit释放缓存并断开 ReplicationSystem 引用。

ObjectIndices 是当前批次列表，但 Priorities 和 PrioritizationInfos 仍以真正的 ObjectIndex 索引。不要写成 Priorities[BatchIt]。引擎源码中的 Sphere Prioritizer 会先把离散对象索引整理成局部连续批次，再做向量化计算，最后写回。

多 View 是正常情况

FReplicationView 里是一个 Views 数组，每个 View 包含 Controller、ViewTarget、位置、方向和 FOV。分屏、子连接或项目自定义视点都可能产生多个 View。通常要取“任一 View 下的最高重要度”，不能默认 Views[0] 就代表整个连接。

17.2B · COMBAT TRIAGE

手把手建模：战斗优先级器

大逃杀或竞技游戏里，纯距离并不等于重要度。远处狙击手、正在伤害你的对象、锁定目标和 owner 控制对象，都可能比近处静态装饰更值得先发。关键是把这些信号压成廉价快照，而不是在 Prioritize 中重跑 Gameplay 系统。

分数模型

Base0.25
In Combat+ 0.55
Locked Target+ 0.60
Recent Damage+ 0.35
Owner Boost+ 0.75
FinalMAX(existing, clamp 0…3)

这些数字只是解释模型的起点，不是跨项目最佳值。它们要与网络 tick rate、对象变化率、连接带宽和其他对象类别一起测。特别是 Base 小于 1 的对象会依靠跨 tick 累积进入候选；若业务代码每帧把它错误重置，就会制造永久饥饿。

Combat flags战斗状态变化bit field无分支或少分支加权

StateBuffer 是量化后的内部网络表示

AddObject 和 UpdateObjects 提供的 StateBuffer 不能因为成员在 gameplay 中是 float，就直接 reinterpret_cast<float*>。要先通过 RepTag / Descriptor 找到成员和 Serializer，再按对应配置解量化。引擎 Mock 里存在直接读取的测试捷径，源码也明确警告它“一般并不安全”。

核心算法骨架 · 快照来源由项目补全 
void UCombatNetObjectPrioritizer::Prioritize(
    FNetObjectPrioritizationParams& Params)
{
    for (const uint32 ObjectIndex :
         MakeArrayView(Params.ObjectIndices, Params.ObjectCount))
    {
        const FCombatPriorityRecord& Record =
            Records[GetRecordIndex(
                Params.PrioritizationInfos[ObjectIndex])];

        float Score = Config->BasePriority;
        Score += Record.bInCombat
            ? Config->CombatBoost : 0.0f;
        Score += WasRecentlyDamaged(Record)
            ? Config->RecentDamageBoost : 0.0f;
        Score += IsOwnedBy(Record, Params.ConnectionId)
            ? Config->OwnerBoost : 0.0f;
        Score += BestViewScore(Record, Params.View);

        Score = FMath::Clamp(
            Score, 0.0f, Config->MaxPriority);

        Params.Priorities[ObjectIndex] =
            FMath::Max(
                Params.Priorities[ObjectIndex],
                Score);
    }
}

别只看“高优先级对象确实先发了”

  • 同时观察 Write Bytes：排序更合理不等于总带宽变大。
FILTER × PRIORITY

VIP 通道和 VIP 排队系统如何协作

演唱会安检先决定谁能进场，场内分诊再决定谁先服务。把两个阶段倒过来不仅浪费计算，还会误以为优先级能绕过权限。Iris 的管线正是先缩集合，再为有变化的候选排序。

Connection少量对象、静态连接关系。
Group队伍、频道、Level 等共享受众。
Dynamic最后处理高频对象 × 连接规则。
Dirty / Resend没有变化就没有状态候选。
Prioritize保留已有值，抬高最重要对象。
Budget包空间、依赖与可靠历史最终裁决。

四条工程推论

01 · NO REVIVAL

不能复活

高优先级不能重新放行已经被 Connection、Group 或 Dynamic Filter 排除的对象。

02 · NO DIRTY

不能造变化

对象没有 dirty state 或 resend 需求时，优先级再高也不会凭空生成复制状态。

03 · NO BANDWIDTH

不能扩带宽

Prioritizer 只重排既有预算；需要更多吞吐要从带宽、频率和数据量解决。

04 · NO POLICY IN FRAGMENT

别把策略塞进 Fragment

Fragment 应专注状态采集和应用；连接相关性放 Filter，竞争顺序放 Prioritizer。

05 · DEPENDENCIES

依赖仍有约束

对象引用、子对象和创建顺序可能要求先发送依赖；这会影响最终写入顺序。

06 · OBSERVABILITY

每阶段都要能解释

排障时分别证明：是否在 scope、是否 dirty、分数多少、为何未写入、接收端是否应用。

推荐调优顺序

先用更便宜的 scope 机制减少对象，再检查 dirty / poll 浪费，最后调整优先级。若先写复杂 Prioritizer，它只会替一个过大的候选集合更精细地排队，CPU 和带宽根因仍在。

17.3A · GAMEPLAY ↔ REPLICATION

ReplicationFragment：特殊快递包裹的装卸接口

FReplicationFragment 把一个或多个 ReplicationState 绑定到 gameplay owner。发送端，它把源状态带进复制系统；接收端，它把收到的状态应用回对象，并可参与 owner 收集、RepNotify、轮询和调试输出。

先区分四个扩展点

扩展点决定什么不决定什么首选时机
NetSerializer一个值如何量化、比较和写位流对象是否对连接可见特殊值表示或压缩
ReplicationFragment状态如何采集、应用和回调连接带宽和 scope特殊生命周期 / 应用语义
Filter对象对某连接是否允许属性编码和 RepNotify动态相关性
Prioritizer候选对象的竞争顺序权威 gameplay 状态项目特有重要度

Traits 是 Fragment 与系统的契约

方向

CanReplicate 表示可作为发送源；CanReceive 表示可接收并应用。服务器和客户端实例可能得到不同组合。

生命周期

DeleteWithInstanceProtocol 把 Fragment 生命周期交给 InstanceProtocol。自行 new 的 Fragment 若忘记它，容易泄漏或悬挂。

状态形态

HasPersistentTargetStateBuffer 让 Fragment 管理接收目标；SupportsPartialDequantizedState 声明可部分解量化。

脏标记与回调

NeedsPoll、Push Traits、HasRepNotifies、NeedsLegacyCallbacks、KeepPreviousState 必须与真实实现匹配。

HasInterpolation 在 UE 5.7.4 仍标记为 “Not implemented”

不要仅设置这个 Trait 就宣称获得了通用网络插值。渲染插值、物理预测或状态平滑仍属于对应 Gameplay / Network Physics 系统。

从简单机制逐层升级

L0UPROPERTY普通复制属性、RPC、RepNotify。
L1Property FragmentFReplicationFragmentUtil 自动创建。
L2FastArray动态集合和增量条目语义。
L3NetSerializer特殊值编码、量化与比较。
L4Custom Fragment特殊采集、应用、持久缓冲和回调。

绝大多数 UObject 只需要覆写 RegisterReplicationFragments，然后调用 FReplicationFragmentUtil::CreateAndRegisterFragmentsForObject。这个工具会根据 Class Descriptor 创建 Property Replication Fragments，并由 ReplicationSystem 管理生命周期。

普通 UObject 的首选做法 
#if UE_WITH_IRIS
void UMyReplicatedObject::RegisterReplicationFragments(
    UE::Net::FFragmentRegistrationContext& Context,
    UE::Net::EFragmentRegistrationFlags Flags)
{
    UE::Net::FReplicationFragmentUtil::
        CreateAndRegisterFragmentsForObject(
            this, Context, Flags);

只有普通属性 Fragment 无法表达特殊接收逻辑、持久目标缓冲或自定义回调时，才值得自己实现 ApplyReplicatedState、PollReplicatedState、CollectOwner 与 CallRepNotifies。

17.3B · A REAL UE 5.7.4 CASE

技能系统 Fragment：用引擎真实案例替代玩具代码

GameplayAbilities 模块中的 FMinimalGameplayCueReplicationProxyReplicationFragment 是很好的生产级样本：它既有自定义 NetSerializer，又需要特殊状态应用、持久目标缓冲、Push / Poll 协作和 RepNotify。

注册链

原创结构骨架 · 对照引擎源码阅读 
FReplicationFragment* CreateCustomFragment(
    UObject* Owner,
    const FReplicationStateDescriptor* Descriptor,
    FFragmentRegistrationContext& Context)
{
    const EReplicationFragmentTraits Traits =
        Context.GetFragmentTraits()
        | EReplicationFragmentTraits::DeleteWithInstanceProtocol;

    FMyFragment* Fragment =
        new FMyFragment(Traits, Owner, Descriptor);

    Fragment->Register(Context);
    return Fragment;
}

FMyFragment::FMyFragment(
    EReplicationFragmentTraits InTraits,
    UObject* InOwner,
    const FReplicationStateDescriptor* InDescriptor)
    : FReplicationFragment(InTraits)
    , Descriptor(InDescriptor)
    , Owner(InOwner)
{
    Traits |=
        EReplicationFragmentTraits::HasPersistentTargetStateBuffer;

    if (EnumHasAnyFlags(
            InTraits,
            EReplicationFragmentTraits::CanReplicate))
    {
        Traits |= EReplicationFragmentTraits::NeedsPoll;
        // 建立发送端 FPropertyReplicationState。
    }

    if (EnumHasAnyFlags(
            InTraits,
            EReplicationFragmentTraits::CanReceive))
    {
        // 只有真实支持时才声明 RepNotify / legacy callback。
    }
}

发送端做了什么

  1. 如果 Fragment 能发送，就创建 FPropertyReplicationState 作为缓存；
  2. Descriptor 支持 Push-based dirtiness 时，把对应 Traits 传播到 Fragment；
  3. PollReplicatedState 先看 Poll flags 与 Push dirty，再比较 GameplayCue 的 source key；
  4. 只有需要时才调用 PropertyReplicationState 采集和比较；
  5. NetSerializer 负责值的量化、相等判断和位流表示。

接收端做了什么

  1. Fragment 声明持久目标缓冲，不让系统每次构造临时外部状态；
  2. ApplyReplicatedState 根据 Descriptor 找到 owner 中的真实属性位置；
  3. 从 Context 取得 raw quantized state，调用该成员对应的 NetSerializer Dequantize；
  4. 根据本地连接是否为 owner，执行 GameplayCue 的特殊接收规则；
  5. CollectOwner 让 legacy receive callback 找到正确 UObject；
  6. CallRepNotifies 在正确阶段触发项目需要的通知。
Serializer 与 Fragment 的分工

Serializer 解决“这个 GameplayCue 代理如何成为量化状态、如何比较和解量化”；Fragment 解决“何时采集、目标缓冲在哪里、接收后如何执行 Cue 语义与回调”。两者协作，但不能互相替代。

为什么不把引擎实现整段复制进项目

  • 该 Fragment 针对 FMinimalGameplayCueReplicationProxy 的数据布局和行为，不是通用技能状态容器；
  • 它依赖对应 Descriptor Traits、Serializer 和 Property Registry 注册；
  • owner connection、LocalTags、bit mask 和 RepNotify 都是 GAS 语义；
  • 版本升级可能改变内部结构，项目应学习模式，而不是 fork 大段源码。

推荐优化顺序：从漏斗上游开始

1 · 减少复制对象、子对象与 Fragment 数量
2 · Push Model 与分级 Poll，消灭无效采集
3 · Streaming Level / Connection / Group / Grid 缩小 scope
4 · 对剩余 dirty 候选做 Prioritization
5 · 调 frequency、delta、packet 与可靠预算
6 · 用 Insights、CSV、日志和坏网复测
7 · 最后评估自定义批处理和引擎扩展

对象数量：空间分区、AOI、休眠各管一层

策略减少什么适合不要混淆
Streaming Level / Group连接 scope明确世界分区、实例、副本不是距离算法
Grid / AOI空间候选开放世界、密集对象不能表达所有权限规则
Dormancy无变化对象的采集 / 发送长期静止或低变化对象不等于不相关

服务器分片：Iris 管复制，不管分布式世界

Iris / ReplicationSystem

  • 管理本系统内 NetObject；
  • 维护连接级 scope 和状态；
  • 过滤、排序、序列化和传输；
  • 处理引用、依赖和复制生命周期。
BOUNDARY

项目在线架构

  • 区域服 / 实例服的负载分配；
  • 玩家与对象跨区 handoff；
  • 跨分片消息和全局事件；
  • 持久化、会话、故障恢复和一致性。
不要把“千人世界”写成“千人单 ReplicationSystem”

一个逻辑世界可以由多个进程、区域或实例组成，每个区域有自己的 NetDriver / ReplicationSystem。对象所有权转移、状态接力和跨区可见性仍要由项目协议设计；Iris 不会自动提供分布式一致性。

17.5 · SYSTEM BOUNDARIES

与 GAS、网络物理和 AI 集成

Iris 是复制框架，不是所有多人 Gameplay 问题的总控层。最稳的集成方式，是保留每个系统自己的权威、预测和回调语义，让 Iris 负责可见性、调度与状态运输。

Ability authority、PredictionKey、预测窗口、服务器接纳 / 拒绝、GameplayEffect 回滚和 GameplayCue 语义。

感知、行为树、导航、决策、作弊敏感信息和权威结果；客户端代理只做表现。

网络物理：状态运输 ≠ 物理预测

Filter 决定一个刚体是否对连接可见，Prioritizer 决定拥塞时它的竞争顺序，Serializer 决定状态如何编码；但位置平滑、预测轨迹、错误修正和重模拟属于网络物理。UE 5.7.4 的 UNetworkPhysicsSettingsComponent 暴露 Default Replication、Predictive Interpolation、Resimulation 和 Render Interpolation 等独立设置。

模式 / 机制目标需要复制什么主要风险
Default Replication追随权威刚体位置、旋转、速度、sleep 等延迟下抖动和 hard snap
Predictive Interpolation平滑推进到预测目标周期性权威状态高速碰撞后的误差
Resimulation回到历史帧重跑输入输入 / 状态历史和校正CPU、历史内存、非确定性
Render Interpolation视觉平滑模拟结果与渲染时间线视觉延迟与穿透

“确定性物理”是项目、平台、固定步长、输入和模拟实现共同达成的约束，不是 Iris 承诺。即使传输完全可靠，不确定模拟也会让重放结果分叉。

AI：复制结果，不复制思考过程

NEAR

近距离 AI

复制精确移动、战斗状态、目标表现和关键 Cue；服务器保留感知与决策权威。

MID

中距离 AI

降低 Poll / 更新频率，只复制宏观姿态、路径意图和阶段，不发每个行为树节点。

FAR

远距离代理

使用聚合状态、表现代理或完全过滤；客户端代理不成为权威 AI，也不持有隐藏感知信息。

相关性也是安全边界

不要把隐身目标、AI 感知黑板、服务器路径、未公开任务或反作弊状态复制到“反正画面不显示”的客户端。数据一旦进入客户端内存，就已经越过安全边界；Filter 应在传输前阻止它。

17.6 · SHIP WITH EVIDENCE

检查表、故障矩阵与学习路径

高级扩展的完成标准不是“类写完了”，而是能证明它比内置方案更合适、在规模下更便宜、失败时能回退，并且在版本升级后仍能快速审计。

扩展前

  • 需求不能被 Owner / Connection / Group / Grid 表达
  • 基线记录对象、连接、scope、dirty 和 bytes
  • 明确项目最低 UE 版本
  • 给出禁用自定义实现的回退路径

实现时

  • 对称处理 Add / Remove / Grow / Deinit
  • 热路径无 UObject 查找和动态分配
  • StateBuffer 按 Serializer 正确解量化
  • Traits 与真实能力完全一致

上线前

  • 多 View、Join、Travel、Reconnect
