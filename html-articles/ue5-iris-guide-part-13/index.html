UE 5.7.4 · Iris Replication System · Part 13

条件复制 同一个 ChangeMask，不同连接有不同答案

对象已经通过过滤，不代表它的每个字段都该发给每条连接。Iris 把生命周期条件、对象实例状态与连接上下文叠成掩码，在发送前裁剪 ChangeMask；条件重新满足时，它还必须补脏并修复增量基线，确保远端看到的是当前真值。

Chapter 01 · Problem Space

第十三部分开场对象能看见，不代表每个字段都该看见

同一个 Pawn 对三条连接可能扮演三种角色：拥有者需要私有装备栏，远端模拟者需要移动提示，晚加入者还需要一份只在初始状态发送的随机种子。对象本身对三条连接都可见，但属性集合不应完全相同。

过滤回答“这个对象要不要存在于该连接”；条件复制回答“对象既然存在，这个成员此刻要不要进入该连接的输出”。

这条边界非常重要。给属性加上 COND_OwnerOnly，并不会阻止远端创建 Actor；它只让非 Owner 连接在发送该对象状态时看不到这个属性。反过来，如果整个对象对某连接都没有价值，应该使用 Iris Object Filtering，而不是给对象里的几十个字段逐个加条件。

PRIVATE

只给拥有者

装备栏、输入确认、私密任务状态适合 COND_OwnerOnly。

PREDICTION

避开自主代理

客户端自己预测的值可只发给 Simulated，避免服务器覆盖本地预测结果。

BOOTSTRAP

只进初始状态

稳定配置或生成种子可用 COND_InitialOnly，晚加入者仍有自己的首次状态。

本篇的三个核心结论

条件是在每连接发送阶段裁剪成员 ChangeMask；Owner、Autonomous、Initial、Physics 是不同维度；条件从“不发”切到“发”时，Iris 必须把当前值重新显露，而不是只打开一个开关。

Chapter 02 · Pipeline

先看全景过滤、脏位与条件是三道不同的门

一个属性最终写进某条连接的包，至少经过三类判断。把它们混在一起，常常会得出“加了条件为什么轮询还在发生”或“属性没发为什么对象还创建了”的错误预期。

GATE 01 · OBJECTObject Filter

整个 Net Object 是否允许进入这条连接的复制作用域？不通过时，后续没有这个对象的成员输出。

GATE 02 · CHANGEDirty / ChangeMask

共享状态里哪些成员发生了变化，或者因为条件切换需要重新发送？

GATE 03 · CONNECTIONCondition Mask

对当前连接，Owner、Role、Initial、Physics 与自定义 active 状态允许哪些成员？

OUTPUTSerialize

只序列化仍留在该连接 ChangeMask 中的成员，并与该连接的基线协作。

ChangeMask 与 Condition Mask 回答不同问题

ChangeMask 表示“什么变了”；Lifetime Condition Mask 表示“当前连接上哪些内置条件成立”；Custom Condition Mask 表示“这个对象实例里哪些自定义成员当前激活”。在 UE 5.7.4 的兼容属性路径中，FReplicationConditionals::ApplyConditionalsToChangeMask 把它们叠加到当前连接的掩码副本上。

Dirty ChangeMask 1110 1010 成员 0、1、2、4、6 有变化
Lifetime Allowed 1011 1110 当前连接屏蔽 1、7
Custom Active 1111 0111 对象实例关闭成员 4
Connection Result 1010 0010 最终只发送 0、2、6

上图只是 8 位概念图。真实协议的 ChangeMask 长度由 Replication State Descriptor 决定；一个成员也可能占多个 bit。关键不是位数，而是：条件裁剪不会改写共享的属性值，只改当前连接本次允许发送的成员集合。

Chapter 03 · Mental Model

建立坐标系声明、对象实例与连接上下文三个轴

为什么同一个 COND_OwnerOnly 属性，在连接 A 上通过、连接 B 上失败？因为最终结果并不只由枚举决定，而是由三类信息共同求值。

AXIS 01声明时条件

GetLifetimeReplicatedProps 把 ELifetimeCondition 烘焙进属性布局和 Iris Protocol。它描述成员的长期规则。

AXIS 02对象实例状态

Owning Connection、Autonomous Connection、ReplicatePhysics、自定义 active mask 和 Dynamic 条件均因对象而异。

AXIS 03连接上下文

当前发送给哪条 Connection？是否是该连接的 initial state？由此产生一套连接专属条件掩码。

“Lifetime” 为什么不能按实例临时注册？

Epic 的条件属性文档强调：属性一旦注册为复制属性，不能在某个实例上取消注册。Iris 在 BeginReplication 时建立描述复制数据的 Protocol，同类型实例共享 Protocol；实例差异放在 Instance Protocol 和运行时条件状态里。

void AConditionalPawn::GetLifetimeReplicatedProps(
    TArray<FLifetimeProperty>& OutLifetimeProps) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);

    // 正确：规则对该类的全部实例稳定
    DOREPLIFETIME_CONDITION(
        AConditionalPawn,
        PrivateLoadout,
        COND_OwnerOnly);

    // 错误思路：不要根据 this 的临时状态决定是否注册属性
}
规则稳定，结果可以变化

声明为 OwnerOnly 的规则是稳定的，但谁是 Owner 可以变化；声明为 Dynamic 的占位规则是稳定的，但运行时可切换到 OwnerOnly、SkipOwner 或 Never。不要把“布局不变”和“发送结果不变”混为一谈。

条件准确语义典型用途常见误解
COND_None没有额外生命周期条件常规复制属性不等于每帧都发；仍要有变化
COND_InitialOnly只在当前连接接收对象初始状态时允许生成种子、稳定初始配置不是只在服务器启动或 Actor Spawn 帧
COND_OwnerOnly当前连接等于对象 owning connection私有状态Owner 不必等于 Autonomous
COND_SkipOwner除 owning connection 外允许拥有者本地已知或预测的值不是“只发 Simulated”
COND_SimulatedOnly当前连接不是 autonomous connection远端模拟提示不是简单的“非 Owner”
COND_AutonomousOnly只对唯一 autonomous connection 允许自主代理专属状态同一对象不能同时有多个 Autonomous
COND_SimulatedOrPhysicsSimulated 或对象已启用 ReplicatePhysics移动与物理同步Physics 不是从属性值自动推断
COND_Custom由对象实例的 active mask 开关按对象启停某成员不是逐连接自定义回调
COND_Dynamic运行时改用另一个 Lifetime Condition；默认允许OwnerOnly 与 SkipOwner 间切换不是任意 Lambda 谓词
COND_Never条件始终不成立Dynamic 的关闭目标、测试或生成布局不是注销复制属性
COND_NetGroup按 SubObject 所属 Net Group 过滤连接子对象分组不能用于属性

Replay 条件需要单独验证

枚举还包含 ReplayOnly、ReplayOrOwner、SkipReplay 及 NoReplay 组合。本文保留它们的公开语义，但不把普通连接的代码路径外推成完整回放实现：本地 UE 5.7.4 的 GetLifetimeConditionals 对普通连接明确启用 COND_SkipReplay，未启用 COND_ReplayOnly；项目若依赖 Replay，应结合实际 NetDriver、回放连接和版本做测试。

Push Model 与条件是正交的

Push Model 解决“系统怎么知道值变了”，Condition 解决“这份变化能发给哪条连接”。Push 属性没有正确 Mark Dirty，条件再正确也没有新 ChangeMask；属性已经脏了，条件不满足时仍会在该连接上被裁掉。

注册条件不是秘密保护

OwnerOnly 能减少不必要的传输，也能避免服务器值覆盖拥有者本地预测值；但网络协议不是安全边界。服务器仍必须对客户端输入做权威校验，客户端二进制也能推断类布局。条件复制负责数据路由，不负责加密或访问控制。

Chapter 06 · Roles

生命周期与角色矩阵Owner、Autonomous、Initial 与 Physics 不是同一个开关

多人游戏里 Owner 与 Autonomous 经常指向同一玩家，于是工程代码容易把它们当成同义词。Iris 5.7.4 的实现明确分开：

  • Owner：来自 ReplicationFiltering->GetOwningConnection(ObjectIndex)；
  • Autonomous：来自 FPerObjectInfo::AutonomousConnectionId，同一对象最多一条连接；
  • Simulated：当前连接不等于 AutonomousConnectionId；
  • Initial：当前连接正在接收该对象的初始状态；
  • Physics：对象级 bRepPhysics，默认关闭。
条件Owner + AutonomousNon-owner + SimulatedLate join + Simulated
COND_OwnerOnly发送屏蔽屏蔽
COND_SkipOwner屏蔽发送发送
COND_AutonomousOnly发送屏蔽屏蔽
COND_SimulatedOnly屏蔽发送发送
COND_InitialOnly仅初始状态仅初始状态自己的首次状态
COND_InitialOrOwner持续允许仅初始状态自己的首次状态

Initial 是“每连接”的

服务器在 10:00 Spawn 一个 Actor，连接 C 在 10:05 加入。对 C 来说，这个 Actor 仍有一份需要首次发送的 initial state，因此 COND_InitialOnly 属性仍应进入 C 的首次状态。它不是“只在 Spawn 那一帧检查”。

Physics 为什么能让 Autonomous 也通过？

COND_SimulatedOrPhysics 的条件是 bRoleSimulated | bRepPhysics。通常 Autonomous 被排除；当对象级 ReplicatePhysics 打开时，即便当前连接是 Autonomous，也允许相关属性。该条件还影响 FReplicatedMovement 的部分成员。

不要用 Owner 推断网络角色

Pawn 的拥有者和自主代理常常一致，但观战、控制权切换、代理对象与自定义复制对象都可能打破这个巧合。需要 Owner 语义就用 Owner 条件，需要 Role 语义就正确设置 RoleAutonomous。

Chapter 07 · 13.2

13.2 ReplicationConditionalsFReplicationConditionals 保存了什么？

FReplicationConditionals 是 UE 5.7.4 Iris 内部把传统属性条件接到每连接发送流程的核心。它不是公开游戏玩法 API，但理解其数据布局，能解释为什么条件切换会产生缓存更新、补脏和基线失效。

PER OBJECTFPerObjectInfo

15 位 AutonomousConnectionId + 1 位 bRepPhysics，描述对象级 Role 与 Physics 状态。

PER CONNECTION × OBJECTObjectConditionals

保存上一套 FConditionalsMask，用于判断某条件是否刚刚从关闭变为开启。

PER OBJECT × REPINDEXDynamicConditions

只为运行时被覆盖的 COND_Dynamic 属性保存实际 ELifetimeCondition。

GLOBAL DIRTY SETObjectsWithDirtyLifetimeConditionals

Owner、Role、Physics 改变后，通知所有有效连接更新全局生命周期条件。

16 位 FConditionalsMask 的边界

FConditionalsMask 内部是 uint16，访问条件时检查索引小于 16，对应属性可用的条件值 0～15。值为 16 的 COND_NetGroup 不塞进这张掩码，而是在 SubObject group 路径单独处理。

struct FConditionalsMask
{
    bool IsConditionEnabled(int Condition) const
    {
        checkSlow(Condition < 16);
        return ConditionalsMask & (uint16(1) << unsigned(Condition));
    }

    uint16 ConditionalsMask;
};

这是兼容属性路径，不是 Iris 最终唯一形态

源码头部注释直言：这个类“几乎所有内容”用于 backward compatibility mode，部分函数较慢；Declared Replication States 可以把很多追踪工作放回状态自身。本文分析的是 UE 5.7.4 中大量现有 UPROPERTY 代码实际会经过的路径，不把它包装成所有未来 Iris 状态的固定形态。

为什么仍然值得读内部实现？

因为它把公开语义落成了可验证的数据结构：Owner 和 Autonomous 确实分开存，Dynamic 确实按 RepIndex 记录，上一条件结果确实按连接缓存，Custom 确实通过额外掩码执行 AND。

Chapter 08 · Runtime

两种运行时机制COND_Custom 与 COND_Dynamic 到底差在哪？

两者都能在运行时改变“发不发”，但改变的东西不同。Custom 改的是 active / inactive；Dynamic 改的是属性当前采用哪一个内置生命周期条件。

BOOLEAN GATE

COND_Custom

改变：该对象实例上，这个成员当前是否激活。

粒度：每对象，不是每连接。

适合：调试快照、可选统计、对象阶段性状态。

不适合：在回调里读取某条连接的 RemoteRole，做逐连接分支。

CONDITION SELECTOR

COND_Dynamic

改变：该对象实例的成员改用 OwnerOnly、SkipOwner、Never 等条件。

粒度：每对象存条件，发送时仍按连接求值。

适合：玩法阶段改变数据受众。

限制：只有初始声明为 COND_Dynamic 的属性可改。

Custom：声明与切换

// GetLifetimeReplicatedProps
DOREPLIFETIME_CONDITION(
    AConditionalPawn,
    DebugSnapshot,
    COND_Custom);

// 对象状态改变时，通过条件管理器切换
DOREPLIFETIME_ACTIVE_OVERRIDE(
    AConditionalPawn,
    DebugSnapshot,
    bReplicateDebugSnapshot);

Epic 官方文档特别提醒：Active Override 是 per actor / per object，而不是 per connection；如果 active 值频繁变化，会带来额外成本。不要把 RemoteRole 或连接专属视图塞进这个布尔表达式。

Dynamic：声明与切换

// GetLifetimeReplicatedProps
DOREPLIFETIME_CONDITION(
    AConditionalPawn,
    TacticalMarker,
    COND_Dynamic);

// 条件发生变化时立即调用，不要拖到 PreReplication
DOREPDYNAMICCONDITION_SETCONDITION_FAST(
    AConditionalPawn,
    TacticalMarker,
    COND_OwnerOnly);

// 也可以在 GetReplicatedCustomConditionState 中设初始条件
DOREPDYNAMICCONDITION_INITCONDITION_FAST(
    AConditionalPawn,
    TacticalMarker,
    COND_SkipOwner);

如果没有运行时覆盖，COND_Dynamic 默认被视为允许复制。测试 DynamicConditionIsReplicatedByDefault 专门锁定了这项行为；不要以为“Dynamic 尚未设置”就等于 Never。

COND_Dynamic

默认允许；等待对象实例选择实际条件。

→
COND_OwnerOnly

只对 owning connection 允许。

COND_SkipOwner

只对非 owning connections 允许。

COND_Never

对全部连接关闭。重新切回可见条件时要补发当前值。

Custom Delta / Fast Array 警告

UE 5.7.4 宏注释指出：Custom Delta 属性（例如 FastArraySerializer）已经复制后再改变 Dynamic Condition，可能产生意外行为。动态条件 setter 应在条件变化时立即调用，而不是依赖 PreReplication 延迟更新。

Chapter 09 · Object State

对象级条件与 SubObjectEReplicationCondition 提供条件输入，不等于属性枚举

ELifetimeCondition 是属性或 SubObject 注册时使用的规则；UE::Net::EReplicationCondition 则是 Iris 对象上的运行时输入。UE 5.7.4 公开两个值：RoleAutonomous 与 ReplicatePhysics。

OWNERSHIPSetOwningNetConnection

设置 owning connection，驱动 OwnerOnly、SkipOwner、InitialOrOwner 等条件，并可能影响对象过滤。

ROLESetReplicationConditionConnectionFilter

5.7.4 只支持 RoleAutonomous；指定连接为 Autonomous，其余连接按 Simulated。

PHYSICSSetReplicationCondition

5.7.4 只支持 ReplicatePhysics；影响 Physics 组合条件与 FReplicatedMovement 的部分成员。

ReplicationSystem->SetOwningNetConnection(
    NetRefHandle,
    OwnerConnectionId);

ReplicationSystem->SetReplicationConditionConnectionFilter(
    NetRefHandle,
    UE::Net::EReplicationCondition::RoleAutonomous,
    AutonomousConnectionId,
    true);

ReplicationSystem->SetReplicationCondition(
    NetRefHandle,
    UE::Net::EReplicationCondition::ReplicatePhysics,
    true);

切换 RoleAutonomous 时，Iris 还会标记 RemoteRole 属性为脏；切换 Owner、Autonomous 或 Physics 时，会让相关对象的全局生命周期条件进入 dirty 集合，并按受影响范围使 delta compression baseline 失效。

SubObject 条件：沿用父对象上下文，但多一条 NetGroup 路径

Bridge 可以为注册的 SubObject 设置生命周期条件。普通条件用 Root/Parent 的条件上下文求值；COND_NetGroup 单独查询该 SubObject 所在的 Net Object Group：

  • Owner group 映射到 OwnerOnly 语义；
  • Replay group 映射到 ReplayOnly 语义；
  • 其他 SubObject filter group 查询当前连接的过滤状态；
  • 父 SubObject 被条件排除时，层级中的子 SubObject 不能越过父节点独立复制。
两个编译期 / 运行期边界

DOREPLIFETIME_CONDITION 会静态拒绝把 COND_NetGroup 用在属性上；COND_Custom 也不用于 SubObject 的连接选择。SubObject 受众需要使用 Bridge 的 SubObject 条件或 NetGroup。

Chapter 10 · 13.3

13.3 条件评估流程共享状态先准备，每条连接再裁剪自己的 ChangeMask

Epic 的 Iris Components 文档把发送端分成 Pre-Send Update 与 Send Update：前者轮询或接收脏通知、复制并量化共享状态、更新过滤和优先级；后者为每条连接调度并序列化对象。属性条件位于后半段的连接专属路径。

1Gameplay Write服务器修改属性
2Dirty DetectPush Mark 或 Poll
3Copy & Quantize建立 Iris 共享状态
4Filter & Schedule决定对象候选
5Lifetime Mask每连接求条件

共享工作：一次准备，多连接复用连接专属：每条连接得到自己的答案

第一步：GetLifetimeConditionals

函数接收 ReplicatingConnectionId、ParentObjectIndex 和 bIsInitialState，计算 Owner、Simulated、Autonomous、Physics 与组合条件，生成 16 位 FConditionalsMask。COND_None、COND_Custom、COND_Dynamic 的基础位默认开启；Custom 的具体 active 状态稍后由另一张掩码处理，Dynamic 还会先替换成实际条件。

第二步：ApplyConditionalsToChangeMask

如果 Protocol 带有 HasLifetimeConditionals Trait，函数遍历带条件的 Replication State Member：

  1. 读取成员声明的 ELifetimeCondition；
  2. 若为 COND_Dynamic，按 ObjectIndex + Property RepIndex 查实际条件；
  3. 条件满足则保留 ChangeMask；若上一轮不满足、本轮满足，则主动设置该成员的所有 ChangeMask bits；
  4. 条件不满足则清除该成员对应 bits；
  5. 最后把 Custom 的 ConditionalChangeMaskData 与结果逐字 AND。
// 逻辑化简，不是 UE 源码逐行拷贝
for (Member : LifetimeConditionalMembers)
{
    Condition = Member.DeclaredCondition;

    if (Condition == COND_Dynamic)
        Condition = GetDynamicCondition(ObjectIndex, Member.RepIndex);

    if (!LifetimeMask.IsConditionEnabled(Condition))
        ConnectionChangeMask.ClearBits(Member.BitRange);
    else if (!PreviousMask.IsConditionEnabled(Condition))
        ConnectionChangeMask.SetBits(Member.BitRange);
}

ConnectionChangeMask &= CustomActiveMask;

单一 Lifetime Conditional State 有一条优化路径；多 State Protocol 会累计每个 State 的 ChangeMask offset。无论哪条路径，原则一致：在连接副本上清位或补位，不破坏共享状态。

Chapter 11 · Cache & Baseline

条件缓存从隐藏到可见，为什么不能只把开关拨回来？

连接 A 上某属性过去一直被 OwnerOnly 屏蔽。服务器期间把值从 10 改成 30；A 没收到这两次变化。后来 A 成为 Owner，如果系统只说“条件现在通过”，原 ChangeMask 可能早已清掉，A 仍保留旧值或默认值。

条件重新满足，不是恢复一条静态规则，而是让远端重新加入当前真值。重新显露必须伴随补脏；使用增量压缩时，还要确保基线仍然适用。

上一条件掩码是“可见性历史”

Iris 在 ConnectionInfos[ConnectionId].ObjectConditionals[ObjectIndex] 保存上一套 FConditionalsMask。本轮求得新掩码后逐成员比较：

  • 上一轮满足、本轮满足：按正常 ChangeMask 发送；
  • 上一轮满足、本轮不满足：清掉该成员 bits；
  • 上一轮不满足、本轮满足：设置该成员 bits，强制当前值进入发送候选。

哪些条件变化会使基线失效？

变化补偿行为失效范围原因
Owning Connection 改变标记条件 dirty旧 Owner 与新 OwnerOwnerOnly / SkipOwner 的可见集合对调
RoleAutonomous 改变RemoteRole 标脏 + 条件 dirty受影响连接Autonomous / Simulated 的可见集合改变
ReplicatePhysics 开启条件 dirty全部连接SimulatedOrPhysics 成员可能重新显露
Custom 关闭 → 开启属性 ChangeMask 标脏全部连接远端可能错过了关闭期间的值

DynamicConditionChangeRequiresBaselineInvalidation 的判断很克制：旧条件只要不是始终允许的 COND_None / 默认 COND_Dynamic，就可能曾经屏蔽连接；新条件只要不是 COND_Never，就可能让某连接重新可见。这时才需要按“可能丢失当前值”处理。

基线失效不是“以后全部全量发送”

它只让受影响对象/连接不再依赖可能过期的 delta baseline，重新建立正确基准。把它理解为条件切换的正确性保险，比理解成永久关闭增量压缩更准确。

性能：条件究竟省了哪一段？

条件主要减少的是每连接成员序列化与带宽，并可避免远端不需要的属性覆盖。它通常不会倒流回去取消已经发生的对象轮询、共享状态拷贝或量化。若一个大字段对 99 条连接都无用，收益很直接；若 4 字节字段每帧高频翻转条件，条件维护和基线修复可能抵消收益。

WHOLE OBJECT对象 Filter

整对象对某连接无用时，从更早的阶段排除，不要给全部成员逐个加条件。

STABLE RULE内置 Condition

Owner、Role、Initial 等稳定规则优先，意图清楚且便于引擎优化。

OBJECT SWITCHCOND_Custom

按对象实例启停成员；不要把它当逐连接谓词，也不要无意义高频切换。

AUDIENCE SWITCHCOND_Dynamic

需要在 OwnerOnly、SkipOwner、Never 等内置受众之间切换时使用。

推荐的测量维度

  • 对象数与平均有效连接数；
  • 条件属性数量和成员 ChangeMask bit 数；
  • 字段尺寸、变化频率与实际压缩率；
  • Custom / Dynamic 条件每秒切换次数；
  • 条件重新显露引发的 baseline invalidation 数量；
  • 过滤、轮询/量化、序列化和发送带宽各自的占比。

Chapter 13 · Debug & Source

排错、源码导航与测试从“对象有没有”一路查到“成员为什么被清位”

排错顺序

  1. 对象是否进入该连接：先看 Object Filter、Group、Dormancy 和调度，不要一开始就怪属性条件。
  2. 属性是否注册：检查 UPROPERTY(Replicated...) 与 GetLifetimeReplicatedProps。
  3. 属性是否脏：Push Model 是否调用 Mark Dirty；轮询对象是否被 Poll。
  4. Owner 是否正确：检查 Iris owning connection，不要只看 UObject 的 Owner 指针。
  5. Role 是否正确：Autonomous connection 是否通过 SetReplicationConditionConnectionFilter 设置。
  6. Initial 判断是否正确：晚加入连接是否真的在接收该对象 initial state。
  7. Custom 是否用官方 API 切换：只改自己的布尔变量，不会自动更新条件掩码。
  8. Dynamic 声明是否匹配：setter 只对原始条件为 COND_Dynamic 的属性生效。
  9. SubObject 父链是否允许：父 SubObject 被过滤时，子节点不能越过父节点出现。
  10. 条件是否在抖动：频繁补脏和基线失效可能让性能与带宽不降反升。

本篇结论

BOUNDARY

先对象，后成员

Object Filter 决定对象范围，Conditionals 在发送前裁剪成员 ChangeMask。

CONTEXT

按连接求值

声明规则、对象状态与连接上下文共同产生 Owner、Role、Initial、Physics 结果。

CORRECTNESS

重新显露要补偿

条件从隐藏到可见必须补脏，并在需要时使 delta baseline 失效。

脏位说“值变了”，条件说“谁能看见”；Custom 改开关，Dynamic 改规则；上一轮条件缓存和基线失效，则保证“重新看见”时拿到的是现在，而不是过去。
