Chapter 01 · Mental Model

先划边界RPC 是一次调用，不是一份状态

玩家扣下扳机时，客户端可能向服务器发送“我要开火”；服务器验证后，再让相关客户端播放枪口火焰。这些都是某个时刻发生的动作。至于弹匣还剩几发、门现在开还是关、回合比分是多少，则是应该长期成立的状态。

DURABLE TRUTH

Replicated Property

描述“现在是什么”。旧更新可以被新状态覆盖；晚加入连接仍能获得当前结果。

OR
ONE-SHOT INVOCATION

Remote Procedure Call

描述“现在做一次什么”。它单向、没有返回值，也不会为晚加入者保留历史。

RPC 全称 Remote Procedure Call。调用端像执行普通函数一样发起它，函数体却在远端的一台或多台机器上执行。UE 的反射和网络代码负责把目标、函数与参数转成网络数据；Gameplay 代码仍需决定调用方向、可靠性和业务权限。

可靠 RPC 只是保证“这次调用会持续重试直到确认”，不会把过去的调用变成可查询、可补给晚加入者的状态。
TRANSIENT

适合 RPC

播放音效、粒子、动画，提交玩家输入意图，触发一次低频控制动作。

CURRENT VALUE

适合属性复制

生命值、弹药、门状态、占点进度，以及任何“后来的人也应看到”的结果。

NO RETURN VALUE

返回要另行建模

用响应 RPC、请求编号或复制状态回传；不要期待网络函数像本地函数一样同步 return。

Chapter 02 · Decision Boundary

先问过期后还有没有价值状态还是事件，不由“重要不重要”决定

需求推荐机制原因反例
枪口火焰、脚步声Unreliable RPC晚到比丢失更糟，下一次事件自然覆盖感知每一帧都 Reliable，网络抖动时积压过期表现
客户端提交开火意图Server RPC + 服务端校验传递意图，权威结果仍由服务器计算客户端直接上报“命中了谁、扣多少血”
当前弹药与生命值Replicated Property只关心最新真值，晚加入者也需要靠一串扣弹/受伤 RPC 重建状态
低频且必须执行的确认Reliable RPC调用本身不可丢，频率足够低高频输入、鼠标移动逐次 Reliable
跨对象业务事务状态机 + Sequence/Epoch网络层不保证不同 Actor 的全局调用顺序假定 Actor A 的 RPC 永远先于 Actor B

一个实用的四问决策法

  1. 晚加入者需要知道吗？需要，就先考虑状态复制。
  2. 旧消息被新值覆盖可以吗？可以，就让最终状态收敛，不要重放全部历史。
  3. 丢失比迟到更糟吗？只有答案明确为“是”，才考虑 Reliable。
  4. 调用方可信么？客户端永远只能提交意图，服务器必须重新验证并决定结果。
“重要”不是 Reliable 的充分条件

玩家位置很重要，但通常依靠连续状态更新与校正；每一帧位置都可靠重传，反而会让旧数据堵住新数据。可靠性要匹配数据的时间价值，不是匹配产品经理口中的优先级。

Chapter 03 · End-to-End

从扣下扳机到远端执行一次开火 RPC 的十站旅程

下面这条链是全文地图。Gameplay 层仍调用一个生成的网络函数，Iris 则把它转换成对象附件，排入连接专属队列，经过序列化、确认与接收校验后，才真正进入远端对象的 ProcessEvent。

01 · GAMEPLAY调用 ServerFire

生成代码判断 callspace；本地或远端路径由角色、方向与连接决定。

02 · NETDRIVERProcessRemoteFunction

检查 Actor 生命周期，复制参数，选择 Iris ReplicationSystem。

03 · APISendRPC

multicast 用无 ConnectionId 重载；unicast 指定目标连接。

04 · MANAGER验证发送资格

方向、连接、Root/SubObject、scope 前提与 dormancy。

05 · CREATE创建 FNetRPC

设置 Reliable / Ordered，定位函数，量化参数并收集引用。

06 · QUEUEAttachment 入队

按连接与目标对象进入普通队列或 OOB attachment queue。

07 · WRITER连接维度调度

检查对象是否已复制、是否在 scope、预算和可靠窗口。

08 · PARTIAL必要时拆片

预序列化，单块 shrink-wrap 或拆成有序 partial blobs。

09 · RECEIVE解析与 Dequantize

解析目标、函数和参数，验证方向与 ownership。

10 · EXECUTEProcessEvent

进入接收 RPC 上下文，调用实际 UFunction，最后析构参数。

十站中任何一站都可能让调用停止

BEFORE QUEUE

发送资格失败

方向错误、连接已关闭、对象尚未复制、SubObject 无法定位。

IN TRANSIT

不可靠数据丢失

包丢了就不重发；对象离开 scope 或已 pending destroy 也可能被丢弃。

BEFORE EXECUTE

接收校验失败

函数定位无效、方向不允许、调用连接不拥有目标或对象已停止复制。

Chapter 04 · 14.1 Overview

Gameplay 表面兼容，运输内核换轨Iris 中的 RPC 与传统 RPC 有何不同

Epic 的迁移文档明确把 Remote Procedure Calls 列为“未改变”的 Gameplay 特性：声明与执行方式保持兼容。你依旧写 UFUNCTION(Server)、Client 或 NetMulticast，依旧实现 _Implementation。

UFUNCTION(Server, Unreliable)
void ServerFire(
    FVector_NetQuantize Origin,
    FVector_NetQuantizeNormal Direction);

UFUNCTION(NetMulticast, Unreliable)
void MulticastFireFX(
    FVector_NetQuantize Origin,
    FVector_NetQuantizeNormal Direction);

改变的是网络层内部载体。传统系统围绕 ActorChannel 与 Bunch 组织 Actor 的属性和 RPC；Iris 把 RPC 表示为 FNetRPC，而它是一种 FNetObjectAttachment。附件随对象或 OOB 队列进入 FReplicationWriter 与 Replication Data Stream。

观察层通用 / 传统复制路径Iris 5.7.4 路径

Gameplay 调用像普通函数一样调用保持兼容
NetDriver 入口ProcessRemoteFunction仍由它进入，但转交 UReplicationSystem
传输载体ActorChannel / BunchFNetRPC : FNetObjectAttachment
排队与写入Channel 体系FNetBlobManager + FReplicationWriter
大负载通用 bunch/partial 机制UPartialNetObjectAttachmentHandler
迁移时大多数 Gameplay RPC 不必重写

但“调用方式兼容”不等于“内部细节相同”。分析带宽、调度、scope、OOB 或 Handler 时，必须使用 Iris 的 Attachment / NetBlob 模型，不能把 ActorChannel 的实现假设照搬过来。

Chapter 05 · Callspace & Ownership

先决定在哪执行，再决定发给谁方向、调用空间与 Owning Connection

生成的 RPC stub 会先判断函数应该在本地执行还是交给网络。调用机器、函数 specifier 和 Actor 的 owning connection 共同决定结果。Iris 接手之后还会再次做结构性方向校验，接收端也不会盲目执行。

Ownership 是安全门，也是路由信息

Server RPC 到达服务端后，FNetRPC::CallFunction 会比较目标对象的 owning connection 与当前接收连接。不是目标 Owner 发来的调用，不会进入 Gameplay 函数。这能挡住“借用别人 Actor 发 Server RPC”的结构性攻击。

通过 ownership 检查，不等于业务合法

拥有角色的客户端仍可能谎报射速、位置、目标和弹药。服务端必须把 RPC 当作“不可信的输入意图”，重新检查冷却、弹匣、距离、视线、序号和游戏阶段。

NetDriver 是两套内部路径的分岔口

在 UE 5.7.4 的 UNetDriver::ProcessRemoteFunction 中，服务端多播会调用无连接参数的 Iris SendRPC；其余远端调用取得 Actor 的网络连接，再调用带 ConnectionId 的重载。一旦进入 Iris 分支，该次调用就直接返回，不再尝试传统 ActorChannel 路径。

排入正确的连接队列SendRPC、单播与多播

SendRPC 返回 true 的准确含义是“成功排队等待复制”，不是“已经写包”，更不是“远端已经执行”。

发送前的四层资格检查

  1. 全局开关：net.Iris.EnableRPCs 必须大于 0，默认是 1。
  2. 方向：客户端不能发送 Client/Multicast 方向的数据，服务端不能反向发送 Server RPC。
  3. 连接：单播目标必须有效且仍为 open；正在关闭的连接只冲刷既有 reliable 数据，不接收新 RPC。
  4. 对象：RootObject / SubObject 必须映射到可发送的 Net Object；非独立复制子对象可尝试借助 replicated outer 作为 caller。

多播不是“无条件复制 N 份”

SendMulticastRPC 在调用时捕获 open connections 作为候选快照，随后每条连接的 writer 仍会检查目标对象是否已经复制、是否在 scope、是否正在销毁。晚加入连接不在当时的快照中，也不会补执行历史多播。

Chapter 07 · Delivery Contract

可靠性是重发契约，顺序是队列契约Reliable、Unreliable、Ordered 与丢包

UNetRPCHandler::CreateRPC 读取 UFunction 标志：FUNC_NetReliable 会设置 ENetBlobFlags::Reliable；所有非 FUNC_NetMulticast 的 RPC 还会设置 Ordered。

UE5.7.4 Iris 类型ReliableOrdered丢包以后典型用途
Reliable Unicast是是ACK 前持续重发低频、必须执行的控制命令
Unreliable Unicast否是不重发；若交付则保持相关单播队列顺序时效性强的输入或提示
Reliable Multicast是否*对已经排入的连接可靠重发极少数必须执行的群体调用
Unreliable Multicast否否丢失即结束音效、粒子、动画等表现

* “否”指没有因为“非 multicast”规则获得 Ordered 标志；不能由此推导不同系统层面的所有顺序细节。

Iris 的 Ordered 实现细节要放在正确边界内

测试源码 TestUnreliableRPCIsOrderedWithReliableRPCToClient 和 Server 方向对应测试表明：对非多播 RPC，可靠—不可靠—可靠调用在交付时可维持顺序；TestUnreliableRPCIsNotResentAfterPacketLoss 同时证明其中的不可靠调用丢包后不会重发。

这并不提供跨 Actor 全局顺序。Epic 的执行顺序文档明确指出，不同 Actor 上 RPC 的原始调用顺序不会在远端重建。跨对象业务必须携带 sequence / epoch，或者把最终结果放进一个权威状态机。

Reliable 的代价不只是多发几个字节

它会占用可靠窗口，并可能让后续相关有序流量等待 ACK。高频 Reliable 输入在丢包环境中最容易形成“过期消息排队，但最新输入到不了”的 head-of-line blocking。

测试源码 TestMultiCastSendImmediateRPC 用行为锁定了这一差异：immediate 多播能在 PostTickDispatch 被客户端收到，而同阶段的普通多播仍在等待后续正常更新。这里的“immediate”是调度含义，不是当前 C++ 调用栈内就让远端执行。

UE5.7.4 的公开 API 边界

SetRPCSendPolicyFlags 把策略记录到函数映射表。当前本地源码中，无 ConnectionId 的公开 multicast SendRPC 会读取该表；带 ConnectionId 的公开 unicast 重载直接调用 SendUnicastRPC，没有读取它。策略使用还受 net.Iris.Attachments.AllowSendPolicyFlags 控制。

休眠不是 RPC 的硬禁区，但可能有隐性成本

  • net.Iris.RPC.AllowOnDormantObjects 默认 true；
  • net.Iris.RPC.AutoNetFlushOnDormantObjects 默认 true；
  • 默认在休眠对象上发送 RPC 时，会隐式请求 NetFlush；
  • 这可能让应同步的属性状态与 RPC 一起重新进入发送路径。
OOB 不能绕过对象存在性与作用域

目标对象必须已经进入该连接的 replicated state，且不能处于 pending destroy。多播也仍受每连接 scope 约束；“更早调度”不是“无视对象生命周期”。

Chapter 09 · FNetRPC

函数调用被压成一份对象附件定位符、量化参数与引用导出

FNetRPC 继承 FNetObjectAttachment。它不是“复制一段函数名字符串加原始内存”，而是借助目标对象的 Replication Protocol 定位函数，用参数描述符量化每个参数，并收集其中需要先让远端认识的对象引用。

函数定位：DescriptorIndex + FunctionIndex

struct FFunctionLocator
{
    uint16 DescriptorIndex;
    uint16 FunctionIndex;
};

struct FReplicationStateMemberFunctionDescriptor
{
    const UFunction* Function;
    const FReplicationStateDescriptor* Descriptor; // 参数布局
};

DescriptorIndex 指向对象协议中的某个 Replication State Descriptor，FunctionIndex 再定位其中的 Member Function Descriptor。后者同时持有 UFunction 和参数描述符。因此每次调用无需发送完整函数名；两端依靠一致协议解释索引。

参数何时量化

FNetRPC::Create 会先追到最顶层 super function，查找 locator，然后立即调用 FReplicationStateOperations::Quantize。这一步把调用栈上的 Gameplay 参数转成 Iris 可长期持有的 quantized state；队列不会在未来某帧再去解引用调用者的临时参数地址。零参数 RPC 则跳过分配和量化。

目标 attachment 与对象一起序列化时，可以省掉冗余 root 引用，只携带必要的 subobject 信息。函数定位符先用 2 bit 表示后续索引占几个 nibble，再按同一宽度写两个索引，小索引因此更紧凑。

24 位长度是安全边界，不是设计预算

FNetRPC 在开头预留 24 位长度，写完 payload 后回填最终 bit 数。理论格式上限是 (1 << 24) - 1 bits，约 2 MiB 减 1 bit；这绝不是建议把 2 MiB 数据塞进 RPC。长度主要用于在解析失败时跳过整段，并核对接收后的 bitstream 位置。

参数中的 UObject 引用也有因果顺序

量化时会收集可导出的对象引用并设置 HasExports。传输层必须让远端先获得引用所需信息，接收端参数才能正确 Dequantize。这是 Part 12“对象引用与依赖”在 RPC 参数上的直接应用。

attachment 完整到达后，UNetRPCHandler::OnNetBlobReceived 构造 FNetRPCCallContext，再让 FNetRPC::CallFunction 完成解析、校验与执行。接收端绝不会把收到的索引直接当作可信函数调用。

6参数与执行

Dequantize 成功，在 RPC 上下文中调用实际函数。

函数或对象缺失时，长度字段帮它安全跳过

ResolveFunctionAndObject 如果找不到对象或函数，不会继续猜测参数布局，而是移动 reader 到 PostNetRPCPos。若正常反序列化结束后实际位置与长度头不一致，源码会报告 bitstream mismatch，修正 reader 并设置错误，确保该 RPC 不被执行。

Dequantize 之后才得到 UFunction 需要的外部参数内存

  1. 按参数 descriptor 的外部尺寸与对齐分配内存；
  2. 初始化需要构造的属性值；
  3. 把 quantized state Dequantize 到外部参数；
  4. 若 Blueprint 派生类覆盖了同名函数，解析实际的 UFunction；
  5. 广播可选的 FForwardNetRPCCallMulticastDelegate；
  6. 建立 FScopedNetContextRPC 和 Receiving 模式；
  7. 调用 Object->ProcessEvent(Function, Parameters)；
  8. 销毁字符串、容器、对象包装等非平凡参数值。
网络包带来的不是一个“可直接跳转的函数指针”，而是一份必须在目标对象协议、权限和执行上下文中重新解释的调用描述。

Chapter 11 · Lifetime & Trust

对象先存在，调用才有落点SubObject 生命周期与服务端安全

RPC 可以目标到 RootObject，也可以目标到 replicated SubObject。FNetBlobManager::GetRPCOwner 会同时维护 caller reference、target reference、root index 和 subobject index：

  • Root RPC：caller 与 target 都是 root；
  • 独立复制 SubObject：caller / target 指向 subobject，并找到所属 root；
  • 不可独立引用的子对象：可尝试用 replicated outer 作为 caller，但 target 仍保留真实对象引用；
  • root 或 subobject 尚未开始复制时，RPC 可能无法创建或排队。

短生命周期 SubObject 的可靠调用

测试源码 TestShortLivedSubObjectReliableRPC 覆盖了短生命周期子对象上的可靠 RPC。正确性依赖对象创建、attachment 与销毁之间的有序关系，而不是“Reliable 自带对象复活能力”。如果目标已进入 pending destroy 或远端从未建立它，writer / receiver 仍然必须拒绝不成立的调用。

SubObject 多播不能绕过受众

TestSubObjectMulticastRPCIsNotReplicatedToNonOwningConnection 锁定了一个重要边界：子对象不在某连接的复制范围内，多播不会仅因为名字叫 Multicast 就把调用送过去。连接必须先有合法的目标对象，RPC 才有执行落点。

开火请求的服务端校验

void ACombatCharacter::ServerFire_Implementation(
    FVector_NetQuantize Origin,
    FVector_NetQuantizeNormal Direction)
{
    if (!CanFireNow()) return;                  // 冷却 / 状态
    if (!HasAmmo()) return;                     // 权威弹药
    if (!IsPlausibleOrigin(Origin)) return;     // 位置容差
    if (!IsPlausibleDirection(Direction)) return;
    if (!AcceptInputSequence(ClientSequence)) return;

    ConsumeAmmoOnServer();
    ResolveHitOnServer(Origin, Direction);
    MulticastFireFX(Origin, Direction);
}
RPC 的参数永远不是权威事实

客户端可以拥有 Actor，也可以构造任意参数和调用频率。Ownership 只证明“谁在发”，不证明“他说的是真的”。伤害、掉落、货币和移动结果都必须由服务器状态推导。

Chapter 12 · 14.4 Transport

四个名字，不是一条串行流水线NetRPC、Handler、Partial 与 Object Blob 的责任边界

大纲把四个类型放在同一节，容易让人误以为普通 RPC 会依次经过它们。源码实际是：UNetRPCHandler 负责 RPC；Partial Handler 是大 attachment 的通用拆片辅助；UNetObjectBlobHandler 则是与 RPC 并列的“超大对象状态”路径。

FNetBlobManager · 注册并协调不同 NetBlob / Attachment Handler

UNetRPCHandler → FNetRPC

创建与接收一次远程函数调用。设置 Reliable / Ordered，定位函数，量化参数，接收端校验后执行。

UNetObjectBlobHandler → FNetObjectBlob

处理超大的 replicated object state。创建 reliable raw object blob，并走专用装配/反序列化路径；不是普通 RPC Handler。

UPartialNetObjectAttachmentHandler · 为过大的 ObjectAttachment 做预序列化、shrink-wrap、拆片与重组；它可以辅助大 RPC attachment，但不是每个 RPC 都必经。

Partial Handler 如何处理大 attachment

  1. 先把 connection-specific attachment 预序列化到临时 bit buffer；
  2. 若完整 payload 放得下，生成一个 FShrinkWrapNetObjectAttachment；
  3. 若缓冲区溢出，按序列拆成多个 partial NetBlob；
  4. 接收端收集并重组完整 attachment；
  5. 组装后再交给原 handler——对 RPC 来说是 UNetRPCHandler。
本地 UE5.7.4 默认值约合字节正确语境

这些值不是网络 MTU，更不是 RPC 参数预算

它们是 Partial Handler 的内部配置默认值。RPC 越大，预序列化、引用导出、拆片、可靠重传和每连接工作越贵。Gameplay 层应该主动让调用参数保持紧凑。

为什么 NetObjectBlobHandler 的接收回调“不该被调用”

对象 Blob 代表巨大的复制对象状态，接收后需要由特殊路径组装和反序列化，而不是像普通 handler 一样把完整 blob 直接交给 OnNetBlobReceived。源码对该回调的预期正是“不应到这里”。因此它属于 NetBlob 基础设施的兄弟分支，不能写进普通 RPC 的必经链。

性能与带宽检查清单

  • 先统计每类 RPC 的每秒调用次数、平均参数 bits 和目标连接数。
  • 高频输入合并、限频并携带 sequence，不逐次 Reliable。
  • 使用 NetQuantize 类型，避免把高精度大结构原样塞入 RPC。
  • 不要在参数里传可由 ID、枚举或当前状态推导出的冗余字段。
  • Multicast 的成本乘以实际可投递连接数，不能只看单次 payload。
  • 让大资产、数组与快照走状态复制、专用 DataStream 或应用层分块。
  • 只在确有首帧延迟收益时使用 OOB / SendImmediate，并测额外包成本。
  • 关注 dormant RPC 引起的 NetFlush 与属性补发。
  • 跨对象时序由业务 sequence / epoch 保证，不依赖网络偶然顺序。
  • 所有 Server RPC 都做频率、范围、状态和权限校验。

从“没有执行”向两端夹查

  1. 调用空间：调用是否真的需要走远端？NetMulticast 是否错误地从客户端发起？
  2. Owning Connection：Client/Server RPC 的目标连接和 Actor ownership 是否正确？
  3. 对象生命周期：Root/SubObject 是否已经 BeginReplication，远端是否已创建，是否正在销毁？
  4. 发送开关：net.Iris.EnableRPCs 是否启用？方向检查是否拒绝？
  5. Scope 与 Dormancy：对象是否对目标连接可投递？休眠是否触发了预期 NetFlush？
  6. 可靠队列：是否被旧 Reliable 阻塞，或 ordered unreliable 超出预算？
  7. 函数协议：两端 descriptor / protocol 是否一致，函数 locator 是否可解析？
  8. 参数引用：参数中的对象引用是否可导出、可解析？
  9. 接收权限：方向和 ownership 是否通过？Gameplay 校验是否主动拒绝？
  10. 执行观察：用 NetTrace / Iris RPC 日志区分“未到达”“未解析”和“执行后被业务拒绝”。

本篇结论

MODEL

事件不是状态

RPC 表示一次调用；权威结果和晚加入者需要的数据仍由复制状态承载。

TRANSPORT

RPC 是 Attachment

FNetRPC 携带目标、函数定位、量化参数与引用，通过连接队列运输。

TRUST

执行前逐层验证

对象、协议、函数、方向、ownership 与 Gameplay 规则缺一不可。

把 RPC 设计好，要同时回答四件事：这是不是一次事件、应该发给谁、丢了或晚了怎么办、远端凭什么允许它执行。
