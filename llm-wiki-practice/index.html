把收藏炼化成上下文：我的 LLM Wiki 实践记录

原文链接：https://bytetech.info/articles/7660125544725348392
这篇更像是我自己的实践记录：为什么开始做 LLM Wiki、怎么冷启动、平时怎么用，以及我踩到的一些坑。

1. 起因：我不想再把好内容扔进收藏夹了

我以前有很多收藏夹。

浏览器里有，微信里有，小红书、X、YouTube、B 站、知乎也都有。每次看到好文章、好视频、好帖子，第一反应都是先收藏，想着“以后有空再看”。

但后来我发现，收藏很多时候只是另一种形式的遗忘。

内容被我存起来了，但没有被我理解；入口被我保留下来了，但知识没有进入我的工作流。更糟的是，在 AI 时代，我每天和各种 Agent 讨论问题、调试代码、做判断、踩坑复盘，这些过程里其实沉淀了很多经验。可是只要 session 一关，它们也会散落在历史记录里，下次遇到相似问题，我还是要从头开始。

这件事让我开始重新思考：

我真正需要的不是更多收藏，而是一个能持续积累、能被 Agent 反复调用的个人上下文。

这就是我开始尝试 LLM Wiki 的原因。

2. 我理解的 LLM Wiki：不是笔记软件，而是给 Agent 用的知识底座

我第一次认真看 LLM Wiki 这个概念，是因为 Karpathy 在 2026 年 4 月发的一篇 gist。

它里面有一句话我印象很深：

The wiki is a persistent, compounding artifact.

我自己的理解是：

LLM Wiki 不是把文章摘抄成笔记，而是让 Agent 把碎片知识编译成一份可以持续复利的知识库。

传统 RAG 更像是“每次临时翻资料”。你问一个问题，Agent 去文档 chunks 里找内容，现场拼上下文，现场推理，回答完就结束了。下次再问类似问题，它又要重新找、重新拼、重新推。

LLM Wiki 的思路反过来：

  • 原始素材保留下来，作为事实锚点；
  • Agent 负责读懂、总结、归类、交叉引用；
  • 新知识会被编织进已有知识网络；
  • 旧页面会随着新信息持续更新；
  • 矛盾、补充、关联关系都会被记录下来。

也就是说，Agent 不只是“读完这篇文章回答我”，而是在帮我维护一个长期存在的知识系统。

3. 炼化，而不是收藏

我现在会刻意区分两个动作：收藏和炼化。

收藏是终点。点了收藏按钮之后，我大概率就不会再看了。

炼化是起点。它要求 Agent 真正读完材料，把里面可复用的观点、判断、经验抽出来，再放进我的知识结构里。

一篇文章如果只是存在收藏夹里，它还是一座孤岛。只有当它和我的项目经历、技术背景、历史决策、踩坑记录发生连接，它才真的变成了我的上下文。

可以被炼化的东西也不只是长文章。它可以是：

  • 一条推文里的关键判断；
  • 一个视频里的核心论点；
  • 一个 GitHub 项目的架构思路；
  • 一次 debugging session 里的踩坑记录；
  • 群聊里同事说过的一句很准的判断；
  • 历史项目文档里沉睡很久的决策背景。

只要里面有可复用的经验，就值得被炼化。

4. 冷启动：先把过去的自己找回来

刚开始搭 LLM Wiki 时，最大的问题是空。

Wiki 里什么都没有，Agent 对我也不了解。这个时候谈个性化学习、知识复利都太早。冷启动阶段最重要的一件事，是尽快把“过去的自己”找回来。

我觉得可以从三个方向做。

4.1 挖历史 Agent 会话

以前我以为 session 关了就什么都没了。后来发现，其实很多 Agent 工具都会在本地保留历史会话。

这些会话里藏着很多有价值的信息：

  • 我当时遇到了什么问题；
  • 中间试过哪些方向；
  • 哪些方案最后被放弃；
  • 我对 Agent 做过哪些纠正；
  • 最后为什么选了某个实现。

这些内容特别适合作为个人 Wiki 的冷启动材料。

我的理想做法是让 Agent 批量扫描历史会话，判断哪些 session 值得沉淀。真正有价值的，就按当时的背景写成经验记录、项目决策或踩坑复盘。

4.2 翻自己的历史文档

博客、技术分享、side project、简历、项目复盘、PRD、方案文档，这些东西往往散落在不同地方。

单独看时，它们只是文件；串起来看时，其实是一个人的经历轨迹。

当这些内容进入 Wiki 后，Agent 对我的理解就不再是“一个开发者”，而是一个更具体的人：做过哪些项目、熟悉哪些领域、踩过哪些坑、有哪些长期偏好和判断模式。

这也是个性化上下文最有价值的地方。

4.3 清空收藏夹

最后是那些积灰的收藏夹。

以前收藏它们，并不代表没价值，只是我没有时间消化。现在可以把收藏列表批量拉出来，让 Agent 先做粗筛和初步炼化。

冷启动不适合追求“每条都深度学习”。量太大时，更现实的做法是先搭骨架：先让 Wiki 里出现概念、主题、来源和基本关联。真正深入理解，可以放到后面的日常使用里慢慢完成。

还有一个提醒：

一定要注意脱敏。

公司内部数据、credentials、敏感业务逻辑、还没公开的项目信息，都要先清理干净。最好把这条规则直接写进 Wiki 仓库的 AGENTS.md，让 Agent 每次操作前都能看到。

5. 日常使用：炼化之后，要马上消费

冷启动之后，我最常用的动作其实只有两个：

  1. 看到一篇好文章或一个好视频，直接丢给 Agent：帮我炼化一下。
  2. 一次复杂任务结束后，告诉 Agent：把这次踩坑和决策沉淀到 Wiki。

但我后来发现，只炼化还不够。

如果只是把内容整理得更漂亮，分好类、打好标签，然后再也不看，那它和收藏夹没有本质区别。只是多花了一些整理时间，还多烧了一点 token。

所以我现在会尽量在炼化后立刻消费。

比如让 Agent 基于我的 Wiki 给我生成一份讲解：

  • 这篇材料最重要的观点是什么；
  • 它和我已有经验有什么关联；
  • 它有没有挑战我之前的判断；
  • 哪些地方我可能没真正理解；
  • 如果要应用到当前工作里，应该怎么做。

我也很喜欢用费曼学习法：让 Agent 提问，我用自己的话解释。讲不清楚的地方，就是还没真正理解的 gap。

如果是一个需要长期学习的主题，我会更倾向于把它做成 stateful 的学习工作区，比如保留 mission、lesson、learning records，让学习可以跨 session 延续，而不是一次性讲完就散。

6. 个性化教学：Wiki 越懂我，Agent 教得越好

LLM Wiki 最吸引我的地方，是它能让 Agent 的讲解越来越贴近我。

如果 Wiki 里记录了我的背景、项目经历、熟悉领域和踩坑历史，Agent 在解释新知识时就能找到更适合我的类比。

比如一个有音视频客户端背景的人在学习 LLM 推理优化，Agent 可以把 KV Cache 类比成视频解码里的参考帧缓存：不是每次都从头解码，而是复用已有上下文做增量推理。

这种解释不是通用教程能稳定给出来的。它依赖个人上下文。

而个人上下文越丰富，Agent 越知道该从哪里讲起、哪些地方可以略过、哪些地方需要多解释、哪些旧经验可以迁移过来。

这就是我理解的知识复利。

7. Wiki 主要是给 Agent 看的

一开始我也想过用 Obsidian 之类的工具，看 Graph View，浏览概念之间的连接。

但当条目和标签变多后，图谱很容易变成一团毛线。看起来很壮观，实际帮助有限。

现在我更倾向于认为：

Wiki 不是主要给人直接看的，而是给 Agent 消费的。人通过 Agent 间接消费 Wiki。

我自己主要有三种消费方式：

  • 即时教学：炼化完一篇材料后，让 Agent 做个性化讲解。
  • 任务前召回：开工前让 Agent 先查 Wiki，看有没有相关经验可以复用。
  • 按需深挖：想了解某个主题时，直接问 Agent“我的 Wiki 里关于这个主题有哪些内容”。

这样用起来比自己翻目录、点链接、看图谱自然得多。

8. 从个人到团队：让下一个人不从零开始

个人 Wiki 解决的是“下次的我不要从零开始”。

团队 Wiki 解决的是“下一个同事、下一个新人、下一个 Agent 不要从零开始”。

团队里的知识更容易散落：飞书群聊、会议纪要、Bug 单、需求文档、MR 评论、值班记录、项目复盘。每个人手里都有一部分上下文，但很少有人能看到完整图景。

如果这些内容能被持续炼化成团队 Wiki，那么新人上手、同事交接、Agent 执行任务时，都可以少走很多重复路。

当然团队场景会更复杂：权限、隐私、维护责任、知识冲突、过期信息，都需要认真设计。但方向上，我觉得它和个人 Wiki 的本质是一样的：

把散落的经验变成可复用的上下文。

9. 我的落地配置思路

如果要真正跑起来，我会优先选择 Git 仓库，而不是 Notion、飞书文档这类 SaaS 知识库。

原因很简单：Git 对 Agent 太友好了。

Agent 可以直接读文件、grep、rg、看 git log、提交变更。所有东西都是本地文本，速度快，成本低，也更适合自动化。

我理想中的配置大概是这样：

  1. 建一个 private Git 仓库，比如 my-llm-wiki。
  2. Clone 到一个固定路径，多台机器尽量保持一致。
  3. 全局 AGENTS.md 或 CLAUDE.md 只放一条路由规则：涉及 LLM Wiki、知识库、炼化、记忆、沉淀时，先读 Wiki 仓库里的 AGENTS.md。
  4. 具体结构和流程都放在 Wiki 仓库自己的 AGENTS.md 里。
  5. Wiki 内部规则也要渐进式披露，不要把所有细节一次性塞进上下文。

我觉得这里最重要的不是装哪个 Skill，而是让 Agent 知道：Wiki 在哪里，什么时候该去看，什么东西该写，什么东西不能写。

10. 马上可以试的三件事

如果要从今天开始，我会先做这三件事：

  1. 冷启动自己：让 Agent 扫描历史会话、个人文档和收藏夹，先建立知识图谱骨架。
  2. 炼化一篇最近看过的好文章：不要只总结，而是让它和已有经验建立连接。
  3. 炼化后马上学习：让 Agent 基于 Wiki 做一份个性化讲解，再用费曼学习法检查自己是否真的理解。

11. 最后

这件事给我的最大启发是：

AI 时代，真正重要的可能不是我收藏了多少信息，而是我能不能把信息持续炼化成自己的上下文。

收藏夹让知识停在那里；LLM Wiki 让知识进入循环。

每一次炼化，都是在给未来的自己和未来的 Agent 铺路。今天沉淀的一条经验，可能会在几个月后的某个任务里，被重新召回，帮我少踩一个坑、少走一段弯路。

这大概就是我愿意继续折腾 LLM Wiki 的原因。
