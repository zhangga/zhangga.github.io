从“查个余额”，到做出一个能分享的小工具

起因很简单：平时会用 OneAgent 的 API，但想看账户余额和 Token 用量，每次都得打开网页、完成登录。次数多了，就想做个随时能看的小工具。

借助 Codex，我先做了 Windows 托盘版：后台定时刷新，点击就能查看额度和用量。用起来后又发现，余额藏在托盘里还是不够直观，于是加上了常驻余额条，再逐步补上拖动、调整大小、记住尺寸等功能。

这次最有感触的是：功能做出来，只是开始；真正顺手，要靠实际使用不断打磨。

比如，内置窗口无法直接复用浏览器里的 SSO 登录状态，就增加了浏览器扩展方案。但扩展做好后，用户又会卡在“怎么加载扩展”“从哪里打开面板”这些步骤上。一句不准确的按钮描述、一段不够具体的指引，都可能让人用不下去。

后来适配 Mac，也体会到了跨平台的成本。打出安装包，不代表别人就能顺利打开。签名和下载隔离检查都需要处理。目前没有 Apple 开发者账号，先通过首次运行脚本解决试用问题，正式分发仍有完善空间。

最近又看到一篇用飞书个性签名展示 Token 消耗的文档，就想把这个能力也接进工具：让今日用量跟着本机查询更新，愿意展示的人可以把它放在自己的飞书名片上。

我希望接入过程尽量简单：在工具里开启同步、复制签名，再到飞书粘贴保存。为了做到这几步，背后要先把服务部署、数据保存和权限配置处理好。最后统一配置了妙笔服务和多维表格，普通用户不需要再各自建表、部署函数或配置开发者凭证。

接入后最直接的问题是：复制到飞书签名里，保存后看到的还是一长串网址。继续排查才发现，飞书实际发来的预览请求与最初的实现假设不同。修好预览后，又发现直接把预览里的链接换成目标网页，会让飞书保存成另一个地址，后续无法再触发动态更新。最后保留原始动态链接，把点击跳转单独处理，才把显示、更新和跳转接到一起。

这次排障让我对“测试通过”有了更具体的认识。接口返回了正确的用量文案，还需要从真实工具点击复制，到飞书里粘贴、等待预览、保存，再重新查看保存下来的链接。少走其中一步，就可能漏掉只在客户端里出现的问题。Windows 飞书里的这条流程做过实测，其他客户端的表现仍需要分别验证。

签名放在个人资料里，展示哪些信息也要让用户自己决定。后来把今日消费和剩余可用额度做成了两个独立选项，点击跳转地址也允许自行设置。OneAgent 登录凭证留在本机，同步时只上传所选范围的用量摘要；暂停和清除分别处理，旧数据也要标明日期、过期状态。做这种对外展示的功能，需要把公开范围、停止方式和数据时效一起想清楚。

这轮开发还暴露了维护两套 Windows 实现的问题：签名先补进了 .NET 版，Rust 版没有同步，拿到安装包时才发现版本和包体都与预期不同。后来把签名迁到 Rust，当前 Windows EXE 约 0.81 MiB，并决定移除 .NET 源码，以后只维护 Rust 客户端。迁移时也保留原来的签名链接和展示选项，先暂停同步，等确认账户与查询范围后再开启。自动测试覆盖迁移和同步逻辑，Rust 版的真实账户、飞书流程仍交给手动验证。

回头看，这个过程带给我的几点体会是：

  • 从自己的真实痛点出发，更容易做出有用的东西。
  • 先做出能用的版本，再根据反馈迭代，比一开始追求完整更有效。
  • 登录、说明和分发体验，也是产品的一部分。
  • 想做到一键接入，就要提前处理好部署、权限和默认设置。
  • 涉及对外展示时，用户要能决定公开哪些信息，也要能暂停和撤销。
  • AI 降低了开发门槛，但真实环境里的测试和判断仍然少不了。

最有成就感的，是一个原本需要反复打开网页的小麻烦，逐渐变成了任务栏上随时能看一眼的信息，愿意分享的部分也能放进飞书名片里。
